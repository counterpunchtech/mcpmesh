# 0.51.0 design — reverse-DNS `_meta` keys, without the coordinated break (#49, #45 ask 1)

Version: **0.50.0 → 0.51.0 (MINOR)**. `API_MINOR` 57 → 58.

Closes **#49**, closes **#45** (its last open ask), which lets **#48** close.

## #45 ask 1: the decision, which is what the ask actually needs

> **Routing** — resolve the target service from per-request `_meta["mcpmesh/service"]` … rather than
> a one-time initialize. **Decide whether routing stays per-session (first request pins the service)
> or becomes per-request.**

No code is required for the first half: `select_service` reads `/params/_meta/mcpmesh~1service` from
whatever the session's first frame is and **never inspects `method`**. Stateless routing already
works; nothing was anchored on the handshake. That was verified in 0.50.0's review.

**The decision: routing stays PER-SESSION.** Recorded here because the ask is a decision, not a task,
and leaving it unmade is what has kept #45 open.

The reasons, in order of weight:

1. **A session is the authorization unit.** `caller_allowed` is computed once, at accept time, from
   the peer's principal against that service's allow list. Per-request routing would mean one
   connection addressing several services under one authorization decision, so the check would have
   to move into the pump and run per frame — turning a bounded accept-time decision into a hot-path
   one, on the exact surface #164/#189 keep finding holes in.
2. **The pump is 1:1 by construction.** It bridges one caller connection to one backend byte stream.
   Per-request routing means multiplexing to N backends over one connection, with N spawned
   processes or UDS connections, N lifetimes, and a demultiplexer for responses. That is a different
   architecture, not a parameter.
3. **The cost of not having it is one extra session.** A caller wanting a second service opens a
   second QUIC stream to the same endpoint — cheap, already supported, already how every client does
   it.
4. **vNext does not force it.** Statelessness removed the *handshake*, not the transport. Our QUIC
   session remains a perfectly valid place to pin a routing decision, and `_meta` riding every
   request does not oblige anyone to *re-read* it every request.

Revisit if someone actually wants one connection to reach several services. Nobody has asked.

## #49: what changes, and why it no longer needs a coordinated break

#49's premise:

> ⛔ **BLOCKED by #45.** This changes the `_meta` key STRINGS mcpmesh puts on the wire, so both ends
> of a session must adopt them together — it must ship WITH the routing/injection rework.

**That coordination requirement is avoidable, and dissolving it is most of this design.** The two
keys have completely different blast radii, and treating them as one thing is what made this look
like a hard break:

| key | direction | who must agree |
|---|---|---|
| `mcpmesh/service` | caller daemon → **remote** daemon | two mcpmesh nodes, possibly different versions |
| `mcpmesh/peer` | daemon → **local** backend | mcpmesh and a **third-party backend process** |

The second is the dangerous one. Backends are not version-locked to mcpmesh — they are somebody's
`kb` daemon reading `_meta["mcpmesh/peer"]`. Renaming that key outright makes every existing backend
silently stop seeing an identity, and a backend that treats "no identity" as "local caller" would
fail **open**. That is not a break worth taking for a SHOULD-level naming convention.

So:

- **Emit BOTH.** `mcpmesh/peer` and `tech.counterpunch.mcpmesh/peer` carry the identical value.
  Existing backends keep working untouched; new ones can read the reverse-DNS key. Same for
  `mcpmesh/service` on the dial side, so an older remote daemon still routes.
- **Accept EITHER.** `select_service` prefers the reverse-DNS key and falls back to the legacy one,
  so a newer daemon serves an older caller.
- **Strip BOTH prefixes.** This is the security half and it is not optional: if the strip only
  covered one, a caller could forge the other and a backend reading it would be reading
  caller-controlled data. `strip_reserved_meta` removes `mcpmesh/` **and**
  `tech.counterpunch.mcpmesh/`.

Net effect: **no coordination, no version gate on either peer, nothing breaks.** #49's own blocker
was a consequence of the rename-in-place shape it assumed, not of the goal.

### The prefix

`tech.counterpunch.mcpmesh/` — the issue's own suggestion, reverse-DNS of the project's domain.

SEP-1788 reserves only `progressToken` and second-label `mcp`/`modelcontextprotocol`, so our
single-label `mcpmesh/` **never collided** and this was always forward-alignment rather than a fix.
Worth stating plainly: nothing was broken, and nothing is being fixed.

### The removal, named rather than left implied

Emitting two keys forever is the cost of not breaking anyone. The legacy `mcpmesh/*` keys are
**deprecated as of 0.51.0 and will be removed at 1.0** — the pre-1.0 policy already says
compatibility is not carried past then, so 1.0 is the natural and only sensible point. Documented in
the protocol doc and in the ledger so a consumer reading either learns it has a migration window
rather than discovering the removal.

## Testing

1. **Both keys are emitted, with identical values** — for `peer` (injection) and for `service` (dial).
   A test asserting only the new key would pass on an implementation that dropped the legacy one and
   broke every existing backend.
2. **Either key routes**: reverse-DNS alone, legacy alone, and both-present (reverse-DNS wins). The
   both-present case matters because that is what this release actually puts on the wire.
3. **Both prefixes are stripped** — including a caller forging `tech.counterpunch.mcpmesh/peer`,
   which is the new attack surface this change creates and the reason the strip must lead.
4. **A conflicting pair is refused, not silently resolved.** A caller sending `mcpmesh/service: "a"`
   and `tech.counterpunch.mcpmesh/service: "b"` is not making a coherent request; picking one would
   let a caller show two different services to two daemon versions.
5. **End-to-end through a real backend**, since every gate in this session found a call site no test
   reached.

### Mutations to run

- the legacy key dropped from either emitter → test 1 fails.
- the legacy fallback removed from routing → test 2 fails.
- either prefix removed from the strip → test 3 fails.
- the conflict check removed → test 4 fails.

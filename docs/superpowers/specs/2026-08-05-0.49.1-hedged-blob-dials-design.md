# 0.49.1 design — hedged dials for a multi-source blob fetch (#83, the follow-up)

Version: **0.49.0 → 0.49.1 (PATCH)**. No control-surface change, so `API_MINOR` stays 55.

**Corrected from the draft, which said 0.50.0 / MINOR.** `RELEASING.md` is explicit — *"BREAKING
changes bump the MINOR, everything else bumps the PATCH"* — and nothing here breaks: no public
signature moves (`HedgePlan` is `pub(crate)`, `race_a_connection`/`transfer_from` are private), no
wire field changes, no caller opts in. It is a latency property of an existing verb. Calling it a
MINOR would repeat exactly what the 0.49.0 gate caught: asserting a version rule whose stated
reasons do not hold.

---

## The gap this closes

All three of #83's asks shipped (`blob_republish`, `blob_fetch { from }`, the relay-readiness wait
on ticket minting). The issue stayed open on one sentence in the 0.40.0 comment:

> "If a room of eight means walking eight timeouts behind a dead publisher, a bounded parallel race
> (or racing the alternates while the publisher's dial is still outstanding) is the obvious
> follow-up, and it needs its own thinking about abandoned dials."

That is the remaining defect, and it is the ordinary case rather than the exotic one. `fetch_from`
tries sources **strictly sequentially**, each bounded by `DIAL_TIMEOUT`. The room-of-eight the
feature exists for — publisher asleep, several recipients holding identical verified bytes — costs
one full dial timeout per source before the one that works is reached. A user watching an
indeterminate progress bar has no way to tell that from a hang.

## The thinking about abandoned dials, which is the whole design

The 0.40.0 comment declined a parallel race for a real reason, not timidity:

> "a race opens connections it then abandons, and every abandoned dial is work on someone else's
> machine."

That objection survives. A blind fan-out across 32 sources makes a healthy fetch — the common case,
where the publisher answers immediately — into 32 dials, 31 of them pure waste inflicted on peers
who did nothing wrong. It also scales the wrong way: the more generous a caller is with `from`, the
more it costs everyone.

**Hedging keeps the objection satisfied instead of overruling it.** Sources are started on a
stagger, not all at once:

- Source 0 (the publisher) starts immediately.
- Only if no connection has been established after `HEDGE_DELAY` does source 1 start — *alongside*
  it, not after it.
- Thereafter one more source enters every `HEDGE_DELAY`, capped at `MAX_IN_FLIGHT_DIALS` at a time.
- The first connection to succeed wins; every other in-flight dial is dropped immediately.

The property that matters: **a live publisher produces exactly zero abandoned dials.** Extra dials
happen only once a source has already failed to answer within `HEDGE_DELAY`, which is precisely the
situation where a caller wants them. The cost is paid by the case that needs it and by no other.

### Race the DIALS, not the transfers

This is the load-bearing decision, and the smaller one is the right one.

The expensive, parallelisable, safely-abandonable part is the **dial** — it is what costs
`DIAL_TIMEOUT` per source, and dropping its future cancels it cleanly. The **transfer** is neither:
concurrent transfers of the same hash into the same `FsStore` would duplicate network work on both
ends, and — the practical killer — `fetch_from` reports progress through a single shared
`TransferProgressState`. Two attempts writing to it would interleave two byte counters into one
stream, which a consumer renders as a progress bar jumping backwards.

So exactly one transfer runs at a time, and every existing progress guarantee holds untouched:
`Started` still fires once, the coalescing stride is unchanged, the shared counter still means a
fetch that resumes on a later source continues rather than restarting.

If the winning connection's transfer then fails — a permission refusal, a missing hash, a mid-stream
reset, a stall past `SOURCE_TRANSFER_TIMEOUT` — hedged dialling **resumes over the remaining
sources**. That is the 0.40.0 review finding ("every failure mode falls through, not only an
unreachable dial") and it must survive this change, because it is the same room-of-eight case: some
recipients republished the hash into a scope granting us, some did not.

### Two corrections found while building it

**1. A winning dial must give its rivals BACK.** The first cut of `HedgePlan` tracked an in-flight
*count*. When one dial won, its rivals were dropped — and silently retired, because a count cannot
say which sources they were. If that winner's transfer then failed (the ordinary room-of-eight case:
some recipients republished the hash, some did not), the fetch resumed **past two or three live
sources it had already connected to and thrown away** — strictly worse than the sequential walk it
replaced, and invisible to any timing test. `HedgePlan` now owns the in-flight *set* and requeues
abandoned rivals.

**2. Sources must be deduped across the whole list, not just against the ticket.** `fetch_from`
filtered alternates against the ticket's endpoint id only. Two `from` entries resolving to one
endpoint — a nickname and its `eid:`, or two people sharing a device — used to cost two sequential
timeouts, which is merely wasteful. Hedged, they become two *simultaneous* dials to one peer, which
is the single shape this feature must not produce. Now deduped across every source.

### Constants

| | value | why |
|---|---|---|
| `HEDGE_DELAY` | 1s | Long enough that a healthy LAN or relay dial completes first and nothing is abandoned; short enough that eight sources are all in flight in seconds rather than minutes. `DIAL_TIMEOUT` is the thing being escaped, so the hedge must be a small fraction of it. |
| `MAX_IN_FLIGHT_DIALS` | 3 | Bounds concurrent work inflicted on other machines regardless of how many sources a caller names. With `MAX_BLOB_SOURCES = 32`, an unbounded race is a 32× amplifier a caller can trigger. |

## What does NOT change

- **The wire.** `blob_fetch { ticket, dest_path, from }` is unchanged, `API_MINOR` stays 55. This is
  a latency property of an existing verb, not a new surface. A caller does nothing to opt in.
- **Source ordering as a preference.** The publisher is still tried first and alternates still enter
  in the caller's order; hedging changes *when* a later source starts, never which is preferred. A
  fetch that would have succeeded on source 0 still succeeds on source 0.
- **Substitution is still impossible.** Bytes stay BLAKE3-verified against the ticket's hash whoever
  serves them. Racing changes who answers, never what they can serve.
- **The error.** A total failure still reports the last failure with the source count.

## Testing

The honest constraint: `DIAL_TIMEOUT`-scale behaviour cannot be staged in a unit test without
waiting real seconds, and this repo has burned a lot of time on timing-based tests that measured the
machine rather than the code.

So the schedule is extracted as a **pure function** and tested exhaustively, with the async path
covering wiring rather than timing:

1. **The hedge schedule is pure and exhaustive**: which source starts at which tick, the in-flight
   cap holding at every step, the cap never starting a source twice, a single-source fetch never
   hedging at all (the common case must be untouched), and the schedule terminating once sources are
   exhausted.
2. **An unreachable first source does not cost a full `DIAL_TIMEOUT`** — the only assertion that
   distinguishes hedging from the sequential walk it replaced. A blackhole address (`127.0.0.1:1`
   with a live endpoint's id; QUIC is UDP, so the dial hangs rather than being refused) ahead of a
   live recipient, asserting the fetch completes in under 10s against a 20s `DIAL_TIMEOUT`.

   **This is a timing assertion, deliberately, and the margin is what makes it legitimate**: 1s
   hedge vs 20s timeout is a 20x separation, not a stopwatch. Measured: 4.75s green, 20.03s with
   the in-flight cap mutated to 1. A tight-margin timing test would measure the machine, which has
   misled this repo twice.
3. **Transfer failure still resumes** over remaining sources — the 0.40.0 review finding, and the
   regression most likely to be reintroduced by restructuring the loop. Already covered end to end
   by `a_fetch_falls_back_to_a_recipient_when_the_publisher_is_gone`, which puts a dialable
   but-cannot-serve source FIRST; it must keep passing unchanged.
4. **One logical transfer**: `Started` once, one terminal frame, and the byte counter never goes
   backwards across a source change — preserved by racing dials only, never transfers.

### Mutations to run

- the in-flight cap removed → the cap test fails.
- `HEDGE_DELAY` applied to source 0 (delaying the publisher) → the single-dial test fails.
- hedging not resumed after a transfer failure → test 4 fails.
- the winner not cancelling the losers → the dial-count test fails.
- source order reversed → test 3's winner assertion fails.

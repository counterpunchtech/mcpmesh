# 0.53.0 design — a dial hint cannot aim at a non-peer (#203)

Version: **0.52.0 → 0.52.1 (PATCH)**. No control-API change; `API_MINOR` stays 59.

The draft said MINOR, on the reasoning that a stored hint which used to contribute an address now
may not. `RELEASING.md` is explicit — *"BREAKING changes bump the MINOR, everything else bumps the
PATCH"* — and nothing here breaks a consumer. Precedent in this repo for non-breaking work at PATCH:
0.49.1, 0.49.2, 0.41.1. Burning a MINOR signals BREAKING to an embedder who pins.

Advances #203. Does **not** close it.

---

## Where this came from

An adversarial review refused an unshipped change for #140 (a reachability pong carrying the peer's
own addresses) on the grounds that it handed a paired-but-hostile peer a standing UDP reflection
primitive. That change was abandoned. But the review's second finding was not about the abandoned
change at all — **it is true of `main` today**:

`PeerEntry.last_addr` is a dial hint, and `stored_dial_addr` attaches its addresses to every dial of
that peer. iroh, before a path is selected, sends each outgoing datagram to **every** known path. And
one writer of that hint already takes its value verbatim from a remote party: `rendezvous` stores an
invite's `inviter_addr_json` unconditionally and unvalidated.

Nothing filtered what those addresses were. Not in mcpmesh, and not in iroh — a sweep of iroh 1.0.3
for `is_loopback|is_multicast|is_link_local|is_broadcast` finds only `is_unspecified` checks on
*local bind* addresses.

## What ships

`stored_dial_addr` drops addresses that can never be a unicast QUIC peer:

**Canonicalized first.** `Ipv6Addr::is_multicast` matches only `ff00::/8` and `is_unspecified` only
`::`, so neither sees through the IPv4-**mapped** form. The draft filtered without canonicalizing and
was therefore **completely bypassable**: `[::ffff:224.0.0.1]:1900` passed every check, and iroh's own
ingest and sender both call `to_canonical()` — turning it back into real multicast strictly *after*
the filter ran. The gate demonstrated it on all three classes.

- **Unspecified** (`0.0.0.0`, `::`). On Linux `0.0.0.0:<port>` reaches localhost, so this is also the
  cheapest half of the internal-scan concern.
- **`240.0.0.0/4`** reserved, and **port 0** — neither is a peer.
- **Multicast** (v4 and v6). A unicast handshake to a group address is meaningless, and it is a way
  to make one host emit traffic to many.
- **Broadcast** (`255.255.255.255`).

**At `stored_dial_addr` — AND at the two dials that never reach it.** The draft claimed
`stored_dial_addr` was "the single function every dial path calls", and that filtering there
"covers the invite path". **It does not, and the gate proved it.** `redeem_invite` deserializes
`invite.inviter_addr_json` straight into `Endpoint::connect` *before* anything is stored, and
`attest_to` does the same with `offer.node_addr_json`. So the motivating scenario — a crafted invite
aiming this node's padded Initials wherever it likes — still happened in full at redemption, which
is the one moment the whole change exists to protect.

`dialable_only` is now applied at all three sites. `stored_dial_addr` covers every dial from a
STORED hint; the two pairing sites cover the addresses that are dialled before storage.

A hint whose addresses are *all* dropped degrades to the bare-id dial — the same fallback an absent
or id-mismatched hint already takes. Never a dial with no addresses and no discovery.

### What is deliberately NOT filtered

Each of these is legitimate, and rejecting it would break real deployments rather than attackers:

| | why it stays |
|---|---|
| **Loopback** | Two nodes on one host is supported, and most of this repo's own suite pairs over `127.0.0.1`. A blanket loopback reject breaks real usage and most of CI. |
| **IPv6 link-local** (`fe80::`) | Ordinary LAN addressing; iroh may select it. |
| **IPv4 link-local** (`169.254.0.0/16`) | APIPA is real when DHCP fails. It is *also* the cloud-metadata range, which makes it the sharpest remaining edge — and precisely the kind of trade that belongs in #203 rather than in a filter added on the way past. |

## What this does NOT do, stated plainly

**It does not close #203.** Three things remain, and none is a filter problem:

- **Arbitrary routable addresses.** A hostile invite can still name any real host. Bounding that
  needs **provenance** — observed-on-an-open-path versus merely-reported — not a destination
  blocklist. `last_addr` is a bare serialized `EndpointAddr` and carries no such distinction.
- **Relay URLs pass through unfiltered, and are a sharper edge than the UDP case this fixes.** The
  draft's rustdoc justified that with "relay transports are not IP destinations we choose", which is
  false — a relay URL in a hint or an invite is chosen by the remote party, and iroh connects on
  demand to any URL handed to it. `wss://victim:8443/` becomes an outbound TLS/WebSocket connection
  to an attacker-chosen host. Left to #203 because the same provenance model is what makes it
  decidable, and guessing a URL policy is how the previous two attempts in this area went wrong.
- **Subnet-directed broadcast** (`192.168.1.255`) needs the local netmask to recognise, and is a
  better amplifier than `255.255.255.255`, which routers drop.

What ships here is the unambiguous part: addresses that are not peers at all. Calling that a fix for
#203 would be the kind of partial-security-fix-as-closure that leaves the real hole behind a "handled"
label.

## Testing

One test, asserting **both directions**, because a filter has two ways to be wrong and the
over-filtering direction is the one that breaks users rather than attackers:

1. **Every non-peer class is dropped** — `0.0.0.0`, `[::]`, v4 and v6 multicast, broadcast — and the
   dial still names the peer.
2. **Every legitimate class survives** — loopback v4/v6, private, IPv6 link-local, APIPA, public.
3. **A mixed hint keeps the good and drops the bad** rather than discarding the whole hint.
4. **An all-bad hint degrades to the bare-id dial**, not to a dial with nothing to dial.

### Mutations to run

- the filter removed → the test fails on the drop assertions.
- the filter widened to reject loopback → the test fails on the survive assertions. **This direction
  matters as much as the other**: an over-eager filter would break same-host pairings and most of
  this repo's own suite, and a test that only asserted "bad things are dropped" would wave it
  through.

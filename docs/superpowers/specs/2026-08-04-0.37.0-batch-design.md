# 0.37.0 batch design — #178, #176, #59

Three independent issues shipped as one release. They share no code; they are batched because each
is small enough that a release per ticket is mostly release-train overhead.

Version: **0.36.0 → 0.37.0 (MINOR)**. Two of the three change behaviour or a `pub` signature in a
published crate, which `RELEASING.md` makes a MINOR pre-1.0.

---

## #178 — `pair` runs a self-enrollment for an embedder that never asked for one

### The gap

`Invite::decode` accepts both the `mcpmesh-invite:` and `mcpmesh-enroll:` schemes, so a
`mcpmesh-enroll:` line pasted into an embedder's ordinary "Join" field runs the #86 enrollment
ceremony to completion. The embedder learns which ceremony happened only from
`PairResult.enrolled_as_self` — *after* the device→user binding is written, and that binding is
irrevocable short of rotating the user key.

Nothing about the outcome is wrong from mcpmesh's side: the scheme and the flag agree, the human
pasted the line and confirmed a SAS. What is missing is the ability for an embedder to **decline a
ceremony it never offered**.

### Decision

Refuse an enrollment line **by default**, before any dial, and make the caller opt in.

- `PairParams.allow_self_enroll: bool`, `#[serde(default)]` → `false`.
- The guard lives at the **ceremony**, not at the control seam:
  `pairing::rendezvous::redeem_invite` takes a new `self_enroll: SelfEnroll` argument
  (`enum SelfEnroll { Refuse, Allow }`), and refuses immediately after `Invite::decode` —
  before the nickname check, before the dial, before the secret is revealed.

  Enforcing in `daemon::redeem` instead would leave every direct caller of the `pub` `redeem_invite`
  unguarded. A required argument makes the un-offered ceremony unrepresentable rather than merely
  unreachable through one path.
- A named enum, not a bare `bool`: `redeem_invite` already takes eight arguments and a ninth
  positional `bool` is unreadable at the call site.

### Refusal

New `ERR_SELF_ENROLL_NOT_OFFERED: i64 = -32052`, carried as a `PairRefusal` so `control.rs`'s
existing downcast maps it onto the JSON-RPC error. Decided from the line in hand, so — like
`ERR_INVITE_EXPIRED` — it reveals nothing about the inviter and is safe to name precisely.

The invite is **untouched**: nothing was dialled and nothing was burned, so the same line still
works if the caller re-submits it having offered the ceremony.

### Pre-screening seam

`pub fn mcpmesh::pairing::is_enrollment_line(line: &str) -> bool` — so an embedder can branch its
copy ("this is a device-enrollment link — continue?") before calling `pair`, without hardcoding
`"mcpmesh-enroll:"`.

The predicate is exported; the `ENROLL_SCHEME` / `INVITE_SCHEME` constants stay private. A `pub
const` invites `line.starts_with(ENROLL_SCHEME)` re-implementations that drift from `decode`'s
actual acceptance rule. The predicate *is* the rule.

It is sound as a pre-screen because `decode` already enforces that the scheme and `as_self` agree —
so for any line that decodes at all, `is_enrollment_line(line) == invite.as_self`.

### Callers

| Caller | `allow_self_enroll` | Why |
|---|---|---|
| `Client::pair`, `Client::pair_as` | `false` | Fail safe. A library caller that did not ask gets the guard. |
| `Client::pair_opts` (new) | caller's | The explicit opt-in. |
| `mcpmesh pair` (CLI) | `true` | The CLI knowingly offers both ceremonies and already renders the enrollment outcome distinctly (`render.rs`). Its operator *is* the person deciding, and #86's shipped hero flow is `invite --as-self` on one device → `mcpmesh pair` on the other. Adding a flag there would break that flow for no safety gain. |

### Surface

`API_MINOR` 44 → 45, `API_VERSION` `"1.45"`. `docs/local-protocol.md` gets the 45 ledger entry, the
new field, and the new error code; the 43 entry gets a forward pointer, since it documents the
version-skew hazard it closed without noting that a current embedder could still be walked in.

## #176 — a timed-out probe supersedes a pong that already arrived

### The mechanism

`probe_peer` takes its ordering ticket **before** the await, so `seq` is probe START order, and
`supersedes(seq, existing) = seq >= existing.seq`. Among overlapping probes the last-started holds
the highest ticket — and being the most contended, it is the one most likely to hit `PROBE_TIMEOUT`.
So its `reachable: false` overwrites an earlier probe's pong and pins a false negative for a full
`REACH_TTL_SECS` (20 s).

This is the mirror image of the case #58 fixed. #58 stopped an *old* probe's timeout from landing on
a *new* probe's pong; the same rule lets a *new* probe's timeout land on an *old* probe's pong. The
invariant neither version states is the real one:

> A timeout is "my dial got no pong". A pong is direct evidence the peer was up at a known instant.
> A timeout must not overwrite a pong that arrived **inside its own window** — during that window
> the peer demonstrably answered, just not on our connection.

This is the same reasoning #89 already applied to a throttled probe ("a refusal is not evidence").

### Fix 1 — evidence-aware ordering

Stamp each committed entry with an `observed: u64` ticket drawn from the same `probe_seq` counter at
**commit** time (start tickets and commit tickets are therefore comparable). Then, in addition to
the existing start-order rule, a probe refuses to commit when all three hold:

- our result is `reachable: false`, and
- the cached entry is `reachable: true`, and
- `cached.observed > our seq` — the cached pong was observed after we started.

It then returns the cached entry, exactly as the existing `Outcome::Superseded` path does.

Self-healing: a peer that genuinely goes down is reported down by the next probe that starts after
the last pong, since that probe's window contains no pong. The stale-positive window is bounded by
one probe cycle, not by the 20 s TTL.

### Fix 2 — in-flight dedup

`reachability_of` spawns a refresh per stale peer with no dedup, so a caller polling `status` faster
than `PROBE_TIMEOUT` spawns a fresh probe per poll. That is the storm that produces the contention
in the first place — the `reach.rs:677-687` note bounds the probe *count* but not the damage.

Add a `probes_inflight: Mutex<HashSet<[u8; 32]>>` to `MeshState`. `reachability_of` spawns only when
the insert is new; the spawned task removes the entry on completion via a drop guard, so a panicking
or cancelled probe cannot wedge the peer permanently.

Fix 1 is the correctness fix and stands alone. Fix 2 removes the condition that made it observable.

## #59 — no embedder signing API

### The gap

`Node` exposes no way to sign bytes with the node's device key. Any embedder doing store-and-forward
handles payloads whose author is not the peer that delivered them; the transport authenticated the
*forwarder*. Attributing the *origin* today means minting a second identity per device, with its own
storage, backup, revocation, and a binding protocol to tie it to the endpoint id — security-critical
code duplicated in every embedder, next to an ed25519 key that already identifies the device.

### Decision

A narrow, domain-separated surface over the **device (endpoint) key** — the identity the transport
already authenticates, so a verifier needs nothing but the `EndpointId` it already has.

In `mcpmesh-trust`, a new `app` module:

```rust
pub fn sign_app(device_key: &SigningKey, domain: &[u8], msg: &[u8]) -> [u8; 64];
pub fn verify_app(endpoint_id: &[u8; 32], domain: &[u8], msg: &[u8], sig: &[u8; 64]) -> bool;
```

Preimage: `APP_SIG_DOMAIN ∥ (domain.len() as u64 LE) ∥ domain ∥ msg`, with
`APP_SIG_DOMAIN = b"mcpmesh/app-sig/1"`.

Two properties this buys, both enforced by the API rather than left to callers:

1. **An app signature is never an mcpmesh signature.** The fixed `APP_SIG_DOMAIN` prefix is one a
   caller cannot escape, so no caller-chosen `domain` can produce a preimage in
   `mcpmesh/join/device-binding/1`, `mcpmesh/introduce/1`, or any future mcpmesh domain — and the
   reverse holds too.
2. **Two app domains cannot collide.** The length prefix means `("ab", "c")` and `("a", "bc")` have
   distinct preimages. Without it, concatenation lets one domain's signature verify under another.

On `Node`:

```rust
pub fn sign_app(&self, domain: &[u8], msg: &[u8]) -> [u8; 64];
pub fn verify_app(endpoint_id: &iroh::EndpointId, domain: &[u8], msg: &[u8], sig: &[u8; 64]) -> bool;
```

`verify_app` is an associated function — verification needs no node, which matters for a consumer
checking a payload it received out of band.

`MeshState` gains the `ed25519_dalek::SigningKey` derived from the already-loaded `DeviceKey`.
`boot_node` already builds one for the roster presence loop; this hoists it so both read one field.
Note `boot_node` backs both `serve_forever` and `NodeBuilder::start`, so the field exists on the
daemon path too — it is held in memory only, alongside the endpoint secret iroh already holds, and
is reachable from no control verb.

**Not** a control verb: signing over the JSON-RPC socket would put the device key's authority behind
an IPC surface for every consumer of the socket, and the ask is specifically an *embedder* seam.

## Deferred: #80 (blob reclaim)

Considered for this batch and dropped, with a reason rather than silence.

iroh-blobs 0.103.0 exposes only **periodic background GC configured at store construction**
(`Options { gc: Option<GcConfig> }`); `gc_run_once` and `Blobs::delete` are unreachable. Turning that
on makes every blob outside the scope table collectable — which includes everything `blob_fetch`
lands, because a fetched blob joins no scope by design (#83). That converts today's
always-works `blob_fetch` → `blob_export` sequence into a race against the GC interval.

Delivering #80 safely needs a liveness root for fetched blobs and a way for an embedder to release
it. That is its own design and its own release, not a rider on this one.

## Testing

Each property below is mutation-tested: break the behaviour, watch the named test fail, restore.

**#178**
- An enrollment line with `SelfEnroll::Refuse` is refused with `ERR_SELF_ENROLL_NOT_OFFERED`, and
  **no dial is attempted** — asserted against an inviter address that would fail differently if
  dialled, so the test distinguishes "refused early" from "refused late".
- An ordinary invite line is unaffected under `Refuse` (the guard is not a blanket refusal).
- An enrollment line under `Allow` still enrolls (the opt-in actually opts in).
- `is_enrollment_line` agrees with `Invite::decode`'s `as_self` for both schemes.
- `PairParams` deserializes without the field, to `false`.

**#176**
- The headline: a `reachable: true` entry observed after a probe started is NOT overwritten by that
  probe's `reachable: false`. Fixture values are chosen so `observed` and `seq` are distinct and the
  assertion fails if either side of the comparison is dropped.
- A genuine transition to down still commits: a probe started **after** the last pong writes
  `reachable: false`.
- The #58 property is unregressed: an older probe's timeout does not overwrite a newer pong.
- Dedup: two concurrent `reachability_of` calls over the same stale peer spawn one probe, and the
  in-flight entry is released after it completes (a second call afterwards spawns again).

**#59**
- Round-trip: `verify_app` accepts a signature made by the matching device key.
- A different `domain` fails; a different `msg` fails; a different endpoint id fails.
- **Cross-domain separation**: a device *binding* does not verify as an app signature and vice
  versa — the same shape as `a_device_binding_is_not_an_endorsement_and_vice_versa`.
- **Length-prefix separation**: `sign_app(k, b"ab", b"c")` does not verify as
  `verify_app(id, b"a", b"bc", …)`.
- `verify_app` returns `false` on a malformed/short signature rather than panicking (it parses
  caller-supplied bytes).

# 0.43.0 design — blob reclaim (#80), and two MCP 2026-07-28 contract asks (#189, #188)

Version: **0.42.0 → 0.43.0 (MINOR)**. `API_MINOR` 48 → 49.

MINOR because #189 changes what reaches a backend on the proxy path. #80 alone would be PATCH: it
is off unless configured.

---

## #80 — unpublished bytes never leave the disk

`blob_revoke` and `blob_unpublish` (0.13.3, #62) closed the *authorization* half: an unpublished
hash is immediately unfetchable. Neither reclaims a byte. `<data_dir>/blobs/` grows monotonically
for the life of the node, so an embedder that has told a user "this file is deleted" cannot deliver
that, and a long-lived node accumulates every blob it ever published or fetched.

### What upstream actually offers, re-verified against iroh-blobs 0.103.0

The issue's research holds, and one of its claims does not:

- `iroh_blobs::store::gc` is a **private module** (`store/mod.rs:11`). Only `GcConfig`, `ProtectCb`
  and `ProtectOutcome` are re-exported at `:20`. `gc_run_once` is `pub` **inside a private module**,
  so it is unreachable. `Blobs::delete` is `pub(crate)`. There is no on-demand sweep to call.
- `FsStore::load_with_opts(path, Options { gc: Option<GcConfig>, .. })` is public, and
  `fs.rs:1427` spawns `run_gc` when `gc` is `Some`. **This is the only door.**
- **The issue is wrong that `BlobScopes::live_hashes()` exists.** Nothing in the tree defines or
  calls it — `grep live_hashes` returns nothing. It has to be written. Recorded here because the
  issue presents it as done and tested, and a plan built on that would have found out late.

Three properties of `run_gc` that shape everything below, read out of its source rather than
assumed:

1. **It sleeps before its first run.** `loop { live.clear(); sleep(interval); ... }` — so a node
   configured with a 24h interval reclaims nothing until it has been up 24 hours. There is no
   sweep at boot and no way to ask for one.
2. **One error kills GC for the process.** `if let Err(e) = gc_run_once(..) { error!(..); break }`.
   Not `continue` — `break`. A single failed sweep silently ends collection until the daemon is
   restarted, with only a log line.
3. **`ProtectOutcome::Abort` skips one run and keeps looping** (`continue`). That is the fail-safe,
   and it is the right shape: a run that cannot read the liveness root must sweep nothing rather
   than sweep against an empty one.

`gc_mark` roots the live set in **tags and temp tags**, then unions whatever `add_protected` added.
`gc_sweep` deletes every blob not in that set.

### The liveness root

The scope table is the exact root. mcpmesh creates **no persistent tags** — `publish_path`'s
`TempTag` is dropped as it returns — so a blob absent from every scope's `hashes` set is referenced
by nothing mcpmesh knows about.

New: `BlobScopes::live_hashes() -> impl Iterator<Item = &str>`, the union of every scope's `hashes`.

**Withdrawn hashes are deliberately NOT live.** `unpublish` records a tombstone in `withdrawn` and
removes the hash from `hashes`; the tombstone lives in the sidecar, not the store, so it survives
the bytes. Reclaiming a withdrawn blob is the entire point of the feature. What changes is that
`blob_republish` of that hash now fails with `NoSuchBlob` instead of `BlobWithdrawn` once a sweep
has run — both refuse, and the tombstone still refuses first while the bytes are still there.

**The fail-safe.** The callback returns `Abort` if the protect set cannot be built. In practice the
snapshot is in-memory and infallible, so the reachable abort case is a defensive one; it is wired
anyway because the cost of the alternative is deleting every blob on the node.

Boot already fails closed one level up: if `ScopeStore::open` fails, `boot.rs:529` disables the
provider entirely, so there is no store to collect against.

### The interaction that decides the default

A blob this node **fetched** is written to the caller's `dest_path` *and* left complete in the
store. It is in no scope. So under GC it is reclaimed — correct in itself (the store copy is a
cache; the user's file is untouched), but it means:

> fetch a blob, wait one interval, `blob_republish` that hash → **fails**.

`blob_republish` requires `store.blobs().has(hash)`. This is exactly #83 ask 2's multi-source
fallback losing its alternates over time. That is a legitimate trade — you cannot both reclaim
unreferenced bytes and keep them — but it is a surprise, so:

**GC is OFF unless configured.** Silent background deletion is a wrong default for a local-first
tool, and this interaction makes it wrong twice.

### Config

```toml
[blobs]
gc_interval = "1h"     # absent → no garbage collection at all
```

`gc_interval: Option<String>`, parsed by the existing `config::parse_duration`.

**The unparseable-value convention is inverted here, deliberately.** Every other duration in the
tree (`grace_period`, `poll_interval`, `max_staleness`) falls back to its default on a typo,
because a typo must never disable a safety property. Here the safety property runs the other way: a
value that falls back to *some* interval would let `gc_interval = "1hh"` start deleting data the
operator never authorized. So an unparseable value leaves GC **off**, with a `warn!` naming the
value.

`MIN_GC_INTERVAL_SECS = 60`. Below it, GC stays **off** with a warning rather than being clamped
up: a clamped value reads back as honoured and is not.

Both refusals are loud. The failure mode is "the feature I asked for did not turn on", which an
operator can see in `status`; the alternative failure mode is deleted data.

### Observability

`status.storage` gains `blobs_gc: Option<BlobsGcInfo>` — `None` means not configured, which is
distinct from "configured and has not run yet".

```rust
pub struct BlobsGcInfo {
    pub interval_secs: u64,
    /// Runs STARTED. `run_gc` gives no completion callback, so this counts entries to
    /// `add_protected`, not finished sweeps.
    pub runs: u64,
    /// Unix seconds of the most recent run start; `None` before the first.
    pub last_run_epoch: Option<i64>,
    /// Hashes protected on the most recent run.
    pub last_protected: u64,
}
```

**No `bytes_reclaimed` field, and that is not an oversight.** `add_protected` fires *before* the
sweep and there is no after-callback, so any number we printed would be a guess. `blobs_bytes` is
already in `status.storage` and is measured by walking the directory — an operator reads reclaim
from that, over time, which is true. Inventing a reclaimed count would be the "overclaimed
guarantee" class the gate keeps finding.

`runs` is the load-bearing field precisely because of `run_gc`'s `break`: a counter that stops
advancing is the only signal an operator gets that collection has died. Documented as such.

**No audit record per run.** A background timer writing to the audit log is an unbounded growth
source, and the audit log is the thing #80 is trying not to be. `tracing::info!` per run.

### Where it wires

`AppBlobs::load` gains a `gc: Option<Duration>` parameter and switches `FsStore::load` →
`FsStore::load_with_opts`. The `ProtectCb` closes over the `Arc<ScopeStore>` and the counters.

`open_fetcher_with_progress` keeps `FsStore::load` and **never** configures GC: its `ScopeStore` is
`ScopeStore::new` — an empty table that is never persisted — so a protect callback reading it would
protect nothing and the sweep would delete every blob the fetcher holds. Stated in the code, not
just here.

## #189 — a caller-supplied identity claim lands beside our authenticated one

Under 2026-07-28 a client writes `_meta["io.modelcontextprotocol/clientInfo"]`. mcpmesh injects
`_meta["mcpmesh/peer"]`. A served backend now sees two identity-shaped keys in one object with
opposite trust properties.

### What we do NOT do

**We do not populate `clientInfo`.** MCP defines it as the *client software's* self-description, not
the principal. Overwriting a client's `name`/`version` destroys information a backend legitimately
wants and would make mcpmesh the only transport that lies about which MCP client is connected.

**We do not strip it, filter it, or validate it in general.** It is legitimate protocol data and
mcpmesh pumps rather than interprets. A backend that reads `clientInfo.name` as an identity has an
authorization bug that no amount of transport filtering can fix, because the field is
attacker-controlled *by design*.

### The one thing we do

A `clientInfo.name` written in **mcpmesh's own principal grammar** — `eid:…` or `b64u:…` — is never
a client naming its software. It is only ever an attempt to look authoritative next to the key that
is. That is #164's shape exactly: a caller writing in our grammar. It gets #164's treatment.

`sanitize_caller_frame` gains a third step: if `params._meta["io.modelcontextprotocol/clientInfo"]`
is an object whose `name` is a string starting with `eid:` or `b64u:`, **the whole `clientInfo`
entry is removed**. Not just `name` — an object whose name is a forgery has nothing worth
preserving, and leaving a `clientInfo` without its required field is worse than leaving none.

Deliberately narrow:

- Nicknames are **not** checked. "bob" is a plausible name for client software, the nickname space
  is unbounded and per-node, and a check there would be both leaky and false-positive-prone.
- A non-string `name`, an absent `name`, a non-object `clientInfo`, any other name — all pass
  verbatim.
- Runs on **every** frame and descends batches, via the same seam, because #164 was precisely the
  bug of a rule that held on frame 1 only.

**Logged once per session, not audited.** A `tracing::warn!` per offending frame is an unbounded
log-growth vector a caller controls — the audit-log DoS class this project has already fixed once
and then reintroduced. The pump carries a `bool` and warns on the first occurrence only.

### The contract

`docs/local-protocol.md`'s identity section states, where it explains `mcpmesh/peer` and not in a
footnote elsewhere: `clientInfo` is **caller-supplied and is not an identity**; `mcpmesh/peer` is
the only authenticated claim in that object; and the `eid:`/`b64u:` removal above, so a backend
author is not surprised by a missing key.

## #188 — MRTR multiplies the rate budget, and the push contract needs restating

Documentation only. No wire change, no `rmcp` bump — this is metering semantics and docs, both ours.

### An MRTR retry is a fresh request, by decision rather than by accident

`[services.*].rate_limit_per_min` is a per-`(service, endpoint)` bucket over proxied requests. Under
SEP-2322 a tool needing one round of input costs **two** requests; two rounds cost three.

We keep "fresh request", and say so:

- There is no correlation id at the mesh layer, and inventing one means parsing MCP request/response
  semantics inside the transport — which mcpmesh deliberately does not do. Every alternative is a
  bigger change to what mcpmesh *is* than the problem justifies.
- A continuation is still a round trip, still costs a backend invocation, and is still the unit the
  limit exists to bound.

`docs/config.md` gains this next to `rate_limit_per_min`, with the sizing consequence stated
plainly: a budget tuned against 2025-11-25 traffic is **2–3× tighter** for exactly the interactive
tools MRTR exists to enable, and the failure surfaces mid-interaction, after the user has already
been asked a question.

### The #91 push contract, updated for 2026-07-28

`docs/local-protocol.md` documents server-initiated pushes as a contract. It stays true for
**notifications**, and SEP-2663's `subscriptions/listen` is a new consumer of that exact shape. What
changes is that the server→client **request** cases it was largely motivated by —
`sampling/createMessage`, `elicitation/create`, `roots/list` — are replaced by MRTR's
`input_required` retry, and SEP-2577 removes `roots`/`sampling`/`logging` from core (functional for
at least 12 months, so **~2027-07-28**).

The doc says which examples survive, which are on the clock and until when, and names the asymmetry
that follows: a push is unmetered while a proxied request is charged, and under MRTR the server can
no longer *ask* over the push channel. Pushing becomes the only free, non-round-tripping channel.
Not a defect today; written down before someone builds a chat overlay on notifications specifically
because they are free.

## Testing

**#80**

- `live_hashes` unit tests: the union across scopes, that a withdrawn hash is absent, and that an
  empty table yields nothing.
- The protect callback: builds the set from the scope table, and returns `Continue`.
- End to end through a real `FsStore` with a sub-second interval: publish blob A, leave blob B
  unpublished in the store, wait past one interval, assert **B is gone and A is still there**. Both
  halves matter — "B is gone" alone passes on a GC that deletes everything.
- Config: absent → `None`; a valid value → `Some`; unparseable → `None`; below the floor → `None`.
  The last two are the ones that keep a typo from deleting data.
- `status.storage.blobs_gc` is `None` when unconfigured and reports `runs > 0` after a sweep.

**#189**

- `eid:` and `b64u:` names removed; a plain name, a non-string name, an absent name and a
  non-object `clientInfo` all pass verbatim.
- Removal happens on a **non-first** frame and inside a **batch** — the two holes #164 was.
- `mcpmesh/peer` injection is unaffected by the presence or removal of `clientInfo`.

**Mutations to run**

- `live_hashes` returns empty → the e2e's "A is still there" half must fail.
- The `Abort` arm replaced with `Continue` → a test that makes the root unavailable must fail.
- The interval floor removed → the config test must fail.
- The `clientInfo` check restricted to frame 1 → the non-first-frame test must fail.
- The batch descent removed → the batch test must fail.

# 0.52.2 design — a stored dial hint contains only what we observed (#203)

Version: **0.52.1 → 0.52.2 (PATCH)**. No control-API type changed; `API_MINOR` stays 59.

Advances #203. Does not close it.

---

## The invariant

0.52.1 filtered *destinations that cannot be a peer*. That was the unambiguous part. It left #203's
actual subject open: an unvalidated, remote-supplied address is still stored and dialled, and
bounding that needs **provenance** — which of a hint's addresses did this node ever reach?

The provenance question dissolves if the answer is "all of them, by construction":

> **Every address in a stored dial hint was observed on an open IP path of a connection this node
> made or accepted.**

`dial_hint::observed_for` already computes exactly that — the open IP paths of a live connection,
relay URLs excluded — and `dial_hint::refresh` has always used it for a live session. The two
pairing writers did not.

| writer | before | after |
|---|---|---|
| `dial_hint::refresh` | observed, IP-only | unchanged |
| `redeem_invite` | **the invite's whole unvalidated address list** | `observed_for(&conn)` |
| `attest_to` | `EndpointAddr::from(remote_id)` — an **address-less** hint | `observed_for(&conn)` |

## What each change buys

**`redeem_invite`.** The tree's own comment called the invite's list *"the pairing-PROVEN dialable
address (we just reached the inviter through it, id-verified)"*. That is true of **at most one** of
the addresses in it. The rest were a remote party's claim persisted as standing dial targets, which
every later dial sprays QUIC Initials at because iroh sends to every known path until one is
selected. The test's failure output on the reverted code shows the shape exactly: a tampered invite
persisted the decoy *and* three of the inviter's IPv6 addresses the loopback redeemer never touched.

**`attest_to`.** This stored `EndpointAddr::from(remote_id)`: a hint with **no addresses**. Not
merely useless — being `Some`, it won the "never downgrade a known hint" fallback and **replaced** a
peer's proven hint with nothing. Latent data loss, found while auditing the writers rather than
reported.

**Relay URLs fall out for free.** `observed_for` filters to IP paths, so after this no writer can
put a relay URL into a stored hint. #203's finding B is closed *for stored hints*; the one-shot
redemption dial still uses the invite's relay URL, which is inherent to bootstrapping.

## Cost, and why it is acceptable

A **relay-only** pairing now stores no hint (`observed_for` returns `None`, which means leave-alone,
never clear). Before, it stored the invite's addresses.

That pairing reached the inviter through a relay, so a relay/discovery dial is what it will keep
using — and the combination that would actually hurt (relay-only pairing *and* `relay_mode =
"disabled"` *and* no discovery) is self-contradictory: you cannot pair over a relay with relays
disabled. `cold_dial.rs`, the test that exists because of #27's cold-start requirement, passes
unchanged.

## What this does NOT do

**It does not close #203.** The one-shot dials at `redeem_invite` and `attest_to` still send to the
addresses a remote party supplied — necessarily, since that is how pairing bootstraps before any
trust exists. 0.52.1's filter removes the un-dialable classes from those, but a routable decoy is
still contacted once. Bounding *that* means changing how pairing bootstraps, which is a different
change and needs its own argument.

## Testing

The change moved **zero tests** — 62 suites, 911 passed, unchanged — which is exactly the call-site
gap this repo keeps finding, so both writers got a test that fails when reverted.

1. **`the_stored_hint_carries_only_the_observed_address_not_the_invites_list`** — a real redemption
   against a real serving inviter, with the invite carrying a **routable** decoy (`203.0.113.9`,
   TEST-NET-3) alongside the genuine address. Routable on purpose: an unspecified or multicast decoy
   would be removed by 0.52.1's filter and prove nothing about *this* change.
2. **The attestation assertion** in `embedded_loopback` — after the ceremony, a stored hint must not
   be address-less. Reverting the write fails it with the empty blob in the message.

Both were verified by mutation, and the attest one twice: the first attempt reported "not caught",
which was true — the assertion did not exist yet.

# 0.52.3 design — the two remaining sites that dial a remote's address list (#203)

Version: **0.52.2 → 0.52.3 (PATCH)**. No API type changed; `API_MINOR` stays 59.

Advances #203. Does **not** close it, and the limits below are the reason.

---

## What this is, and what it replaced

The attempt immediately before this one capped the address list an invite could make us dial. It was
**abandoned unshipped**: the cap bounded the wrong input (iroh runs address lookup on every fresh
dial regardless), it selected by `BTreeSet` order and so would have dropped the LAN address, the
public v4 and every IPv6 on a multi-homed host, and — because relay entries sort first and are
unfiltered — it guaranteed an attacker's relay URLs were what survived.

This ships the *subtractive* half instead, at the two sites the audit missed. Same shape as 0.52.1
and 0.52.2: remove what can never be a peer, choose nothing, cap nothing.

## Two more sites, both found by review rather than by my own audit

**1. `RosterAddrBook::note`.** `on_announce` parses a blob ticket off the gossip topic and records
its `EndpointAddr` into iroh's `MemoryLookup` — **before** the roster blob is fetched and long before
its org-root signature is checked. Everything recorded becomes a candidate path iroh sends padded
Initials to. 0.52.1's filter guarded the *dial* paths; this one reaches the network through *address
lookup*, so it was untouched.

**2. `AppBlobs::fetch_from`, source 0.** The `alternates` were already filtered — they resolve
through `stored_dial_addr` — but the ticket's own address was pushed raw. Fourth site of this exact
shape, after the invite, the attestation offer and the announce.

Both now pass `dialable_only`.

## The limits, stated because they are large

**Filtering the announce barely helps in the default configuration.** Nothing binds a ticket's `id`
to a roster member, and `blobs.fetch` resolves the provider **by id**, which triggers address lookup.
On `presets::N0` that is pkarr + DNS, and a pkarr record is *self-signed by the endpoint key* — so an
announcer generates a key, publishes any address list they like under it, and that list reaches the
path set with no hygiene whatsoever. The filter is decisive only where the ticket is the sole source:
a discovery-less deployment.

That is the same finding that killed the cap attempt, applied to this site. **Bounding the rest means
constraining address lookup itself**, not filtering blobs at call sites — and that is the shape any
real fix for #203 now has to take.

**Relay URLs are not filtered anywhere**, and at the announce site that is worse than at the pairing
invite: `dialable_only` passes every non-`Ip` variant, iroh opens an outbound TLS connection to any
relay URL handed to it, and unlike a redemption this path is automatic, unattended, and repeatable at
the announce rate limit.

**Addresses-per-entry are still unbounded.** Deliberately: bounding means choosing which to keep, and
the abandoned attempt is direct evidence that choosing wrong breaks the hosts that need it most.

## A correction to the first cut of this change

It kept a duplicate `EndpointAddr` per id in `RosterAddrBook`, on the premise that `MemoryLookup`
exposes no reader and the recording was otherwise unobservable. **That premise is false** —
`MemoryLookup::get_endpoint_info` exists on the pinned iroh. So the duplicate was unnecessary state,
and worse, the test seam built on it observed a *sibling copy* rather than the sink it was meant to
prove. `recorded_for` now reads `MemoryLookup` itself.

## Testing

Both sites are pinned **at the call site**, not through the filter helper — the first cut of this
change asserted `dialable_only` directly and *both* mutations passed, which is the third occurrence
of that failure in this session.

1. **`a_gossiped_ticket_address_is_filtered_before_it_reaches_address_lookup`** — notes a hostile
   ticket into a real `RosterAddrBook` and reads back what reached `MemoryLookup`.
2. **`a_blob_tickets_own_address_is_filtered_before_it_is_dialled`** — builds the fetch's source list
   through a `sources_for_test` seam, since the dial itself needs a live provider.

### Mutations to run

- `note` not filtering → test 1 fails, printing the un-dialable addresses.
- blob source 0 pushed raw → test 2 fails.

Both verified. The no-book fallback in `on_announce` is filtered but **unpinned and unreachable** —
`MeshState` is the only `DistributionHost` and boot always registers a book — which is stated in the
code rather than papered over.

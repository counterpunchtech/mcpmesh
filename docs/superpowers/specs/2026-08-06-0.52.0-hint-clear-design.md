# 0.52.0 design — `peer_hint_clear`, the experiment #140 needs (#140)

Version: **0.51.0 → 0.52.0 (MINOR)**. `API_MINOR` 58 → 59.

Does **not** close #140.

---

## The mechanism, derived from code rather than guessed

#140: two machines on one LAN cannot hole-punch as a **long-lived pairing**, while punching in ~23 ms
with **fresh identities** on the same hardware and the same network. Relayed connectivity is healthy.
It survives restarts, dial-backs in both directions, and live sessions in both directions.

Three facts in this tree, each verifiable without hardware, compose into an explanation:

1. **`PeerEntry.last_addr` is the only durable per-peer state on this node's disk THAT THE DIAL PATH
   READS** — and the only such state a long-lived pairing has that a fresh identity does not. The
   scope matters: a long-lived identity carries other durable state (a published discovery record,
   accumulated `services`, `identity_conflict_epoch`), none of which the dial reads. An earlier
   comment on #140 said "exactly one durable difference" unscoped, and retracted it.
2. **A stale hint is never invalidated.** `observed_for` deliberately returns `None` for a
   **relay-only** connection — persisting a relay URL over a direct candidate was itself a bug
   (#124's review) — and the caller treats `None` as *leave alone*, not *clear*. So on a pair whose
   every connection is relayed, the hint written before the network changed is never refreshed.
   (Other paths DO overwrite it wholesale — `set_last_addr` replaces rather than merges, invite
   redemption writes the inviter's address, and `peer_remove` + re-add drops it at the cost of the
   pairing stamp. "No path removes an address from it" was the draft's phrasing and is false.)
3. **iroh skips address lookup while a path is already selected**, and a selected path is cleared
   only when the last connection to that peer closes. Verified in iroh 1.0.3:
   `trigger_address_lookup` early-returns on `selected_path.is_some()`, and `handle_connection_close`
   clears it only once `connections.is_empty()`. (The draft cited `PeerEntry::last_addr`'s rustdoc
   for this; that rustdoc discusses the merge, not the selected-path condition.)

Compose them for a pairing that holds a live session — which #140's reporter explicitly has, in both
directions:

> A relayed connection is open, so a path is selected. A new dial contributes the stored hint's
> addresses as `Source::App` candidates — all dead, from before the network change — and the address
> lookup that would find the *current* ones is skipped because a path is already selected. The dial
> relays. That connection keeps a path selected. Repeat forever.
>
> A fresh identity has no hint and no open connection, so lookup runs and it punches in 23 ms.

This also explains why #124 helped the reporter's **WAN** peer at the same moment it did nothing
here: there, a connection did open a direct IP path, so `observed_for` returned something and the
hint was refreshed.

**It is a hypothesis, not a diagnosis.** It fits every observation in the issue, and it is still
built on iroh internals read rather than measured on the affected hardware.

## What ships: a tool for a SEQUENTIAL experiment

```
peer_hint_clear { peer }        → { cleared, forgotten }
mcpmesh internal peer hint-clear <peer>
```

Clears `PeerEntry.last_addr` for **every device the selector names** and hands the removed values
back. Nothing else — the row, its `user_id`, its services and its pairing stamp are untouched.

### The experiment must change ONE variable at a time — the draft's did not

The draft prescribed: clear on both ends → stop every session → probe; *"if it punches, the fix is a
hint-invalidation policy."* **That inference is invalid, and the gate caught it.**

Under the very mechanism above, **step 2 alone is sufficient**: closing the last connection clears
iroh's selected path, so the next dial triggers address lookup, discovery finds the current
addresses, and it punches — with the stale hint still in the store, contributing dead `Source::App`
candidates *alongside* the good ones. Bundling the two variables and then attributing the result to
the hint is exactly how a fourth release gets aimed at the wrong thing.

So the procedure, and the CLI prints it:

- **A. Without clearing anything**: stop every session so the last connection closes, **wait >60s or
  restart both daemons**, then probe. A punch here indicts the **selected-path condition**, and the
  hint is innocent.
- **B. Only if A still relays**: clear on both ends, repeat A's steps, probe again. A punch *now*
  indicts the **stored hint**.

The wait is not optional and the draft omitted it. `clear_last_addr` touches redb only; every earlier
dial already inserted the hint's addresses into iroh's per-remote map, and that state is reaped
`ACTOR_MAX_IDLE_TIMEOUT` (60s) after the last connection closes. Probing immediately after step 2
measures a candidate set that still contains the addresses you just cleared — a false negative. This
tree documented that reap to the reporter in 0.49.2 and then left it out of the procedure that
depends on it.

### What it deliberately is NOT

- **Not automatic.** No policy change: nothing clears a hint on its own. Choosing an invalidation
  rule — after N relayed connections? on a network change? — before the data exists is precisely
  what produced #124, which helped one peer and not this one.
- **Not a fix for #140, and the issue stays open.**
- **Not authorization** — the row, `user_id`, services and pairing stamp are untouched, and
  `last_addr` is never an admission input.
- **But not harmless either, and the draft called it "not destructive".** With
  `[network] relay_mode = "disabled"` the node runs with **no discovery at all** — that posture is
  precisely why the hint exists (#27: "a cold daemon able to reach a paired peer even with discovery
  disabled") — so clearing it makes the peer unreachable until re-pairing. And on the relay-only
  pairing this verb targets, `dial_hint::refresh` will never rewrite it, because `observed_for`
  returns `None` for a relay-only connection. There is no `peer_hint_set`. The removed hints are
  therefore RETURNED in `forgotten` and printed by the CLI: that is the undo.

## Surface details

- **Idempotent.** Clearing a peer with no hint returns `cleared: 0` and commits nothing — same
  abort-rather-than-commit discipline `set_last_addr` uses, for the same reason: an empty
  transaction still costs a ~6 ms fsync under redb's global writer lock.
- **Unknown peer is an ERROR** (`-32000`, the generic code the resolver's `anyhow` maps to — the
  draft claimed `-32040`, which is `ERR_NO_SUCH_SERVICE` and would never have matched an embedder's
  branch). An operator must not be told they cleared a hint for a peer this node never paired with.

  **This needed its own resolution path.** `resolve_peer_endpoint`'s `eid:` arm decodes a principal
  and returns it WITHOUT consulting the store, so the first version answered `cleared: 0` for an
  unpaired `eid:` — indistinguishable from a known peer with no hint, and the exact outcome four doc
  sites claimed was impossible. It also returns ONE endpoint for a `b64u:` user_id, which is finding
  4 below.
- **A `b64u:` clears EVERY device of that person.** Since #186 the racing dial path attaches the
  stored hint for each device, so clearing whichever sorted first in redb's key order would leave the
  pairing still addressing from stored state while reporting success — on the two-device fleet in
  #140, the difference between the experiment working and quietly proving nothing.
- **Audited** as a `trust` event. It changes how this node dials a peer, and #140 is a debugging
  session across two machines where "what did we actually do, and when" is the whole record.

## Testing

1. **The hint is gone and NOTHING else moved** — `user_id`, `services`, `nickname`, `paired_at` all
   intact. Asserted field by field rather than "the row still exists": a clear implemented as a
   delete-and-reinsert would pass the weaker check while dropping the pairing proof.
2. **Idempotent**: a second clear returns `cleared: 0`, and the row is still intact after it.
3. **Unknown peer errors on ALL THREE selector forms**, and clears nothing. The `eid:` case is the
   one that was broken; a test covering only the nickname is why the whole workspace was green.
3b. **A `b64u:` with two devices clears both**, asserted per device.
4. **The dial actually changes**: `stored_dial_addr` returns a bare-id `EndpointAddr` after the
   clear, where it returned the hint before. This is the property the verb exists for, and asserting
   only the stored row would leave the dial path unpinned — the failure every gate in this session
   has found.
5. **End to end through the real control socket.**

# 0.52.0 design — `peer_hint_clear`, the experiment #140 needs (#140)

Version: **0.51.0 → 0.52.0 (MINOR)**. `API_MINOR` 58 → 59.

Does **not** close #140.

---

## The mechanism, derived from code rather than guessed

#140: two machines on one LAN cannot hole-punch as a **long-lived pairing**, while punching in ~23 ms
with **fresh identities** on the same hardware and the same network. Relayed connectivity is healthy.
It survives restarts, dial-backs in both directions, and live sessions in both directions.

Three facts in this tree, each verifiable without hardware, compose into an explanation:

1. **A long-lived pairing carries exactly one thing a fresh identity does not** — `PeerEntry.last_addr`,
   the persisted dial hint. Nothing else durable feeds the dial path.
2. **A stale hint is never invalidated.** `observed_for` deliberately returns `None` for a
   **relay-only** connection — persisting a relay URL over a direct candidate was itself a bug
   (#124's review) — and the caller treats `None` as *leave alone*, not *clear*. So on a pair whose
   every connection is relayed, the hint written before the network changed persists **forever**.
   There is no path that removes an address from it.
3. **iroh skips address lookup while a path is already selected**, and a selected path is cleared
   only when the last connection to that peer closes (documented in `PeerEntry::last_addr`'s own
   rustdoc, and re-verified against iroh 1.0.3 by the 0.49.2 review).

Compose them for a pairing that holds a live session — which #140's reporter explicitly has, in both
directions:

> A relayed connection is open, so a path is selected. A new dial contributes the stored hint's
> addresses as `Source::App` candidates — all dead, from before the network change — and the address
> lookup that would find the *current* ones is skipped because a path is already selected. The dial
> relays. That connection keeps a path selected. Repeat forever.
>
> A fresh identity has no hint and no open connection, so lookup runs and it punches in 23 ms.

This also explains why #124 helped the reporter's **WAN** peer at the same moment it did nothing
here: there, a connection did open a direct IP path, so `observed_for` returned something and the
hint was refreshed.

**It is a hypothesis, not a diagnosis.** It fits every observation in the issue, and it is still
built on iroh internals read rather than measured on the affected hardware.

## What ships: the experiment, not the fix

```
peer_hint_clear { peer }        → { cleared: bool }
mcpmesh internal peer hint-clear <peer>
```

Sets `PeerEntry.last_addr` to `None`. Nothing else — the peer row, its `user_id`, its services and
its pairing stamp are untouched.

**Why this and not a fix.** Clearing the hint makes an existing pairing *addressing-equivalent to a
fresh identity*, which is the exact difference #140 is about. So the reporter can run the
discriminating experiment on the hardware that reproduces it:

1. `peer_hint_clear` on both ends.
2. Stop every session between the two, so the last connection closes and iroh's selected path clears.
3. Probe fresh.

If it punches, the hypothesis holds and the fix is a hint-invalidation policy. If it still relays,
the hint was never the cause and three releases of dial-path changes have been aimed at the wrong
thing — which is worth knowing before a fourth.

**It is also a workaround** if the hypothesis holds: an operator can unstick a pair today.

### What it deliberately is NOT

- **Not automatic.** No policy change: nothing clears a hint on its own. Choosing an invalidation
  rule — after N relayed connections? on a network change? — before the data exists is precisely
  what produced #124, which helped one peer and not this one.
- **Not a fix for #140, and the issue stays open.**
- **Not destructive.** A hint is advisory addressing, never authorization, and its absence is a
  supported state (`stored_dial_addr` degrades to an id-only dial, which is what every freshly
  paired peer does until its first refresh). The worst case is one slower dial while discovery runs.

## Surface details

- **Idempotent.** Clearing a peer with no hint returns `cleared: false` and commits nothing —
  same abort-rather-than-commit discipline `set_last_addr` uses, for the same reason: an empty
  transaction still costs a ~6 ms fsync under redb's global writer lock.
- **Unknown peer** → `-32040`, the existing not-found code, rather than a silent success. An
  operator running the experiment must not be told they cleared a hint for a nickname they typo'd.
- **Audited** as a `trust` event. It changes how this node dials a peer, and #140 is a debugging
  session across two machines where "what did we actually do, and when" is the whole record.

## Testing

1. **The hint is gone and NOTHING else moved** — `user_id`, `services`, `nickname`, `paired_at` all
   intact. Asserted field by field rather than "the row still exists": a clear implemented as a
   delete-and-reinsert would pass the weaker check while dropping the pairing proof.
2. **Idempotent**: a second clear returns `false`, and the row is still intact after it.
3. **Unknown peer errors**, and clears nothing.
4. **The dial actually changes**: `stored_dial_addr` returns a bare-id `EndpointAddr` after the
   clear, where it returned the hint before. This is the property the verb exists for, and asserting
   only the stored row would leave the dial path unpinned — the failure every gate in this session
   has found.
5. **End to end through the real control socket.**

### Mutations to run

- the clear writing `Some("")` rather than `None` → test 4 fails.
- another field cleared alongside → test 1 fails.
- the unknown-peer branch returning `Ok(false)` → test 3 fails.
- the dispatch arm deleted → test 5 fails.

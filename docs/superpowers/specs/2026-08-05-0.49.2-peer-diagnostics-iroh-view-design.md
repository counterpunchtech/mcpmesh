# 0.49.2 design — `peer_diagnostics` gains iroh's own view (#140)

Version: **0.49.1 → 0.49.2 (PATCH)**. Additive fields on an existing verb. `API_MINOR` 55 → 56.

---

## Corrected scope, after reading what already exists

The draft proposed a new `peer_paths` verb. **`peer_diagnostics` already exists** (`api_minor` 33,
shipped for this same issue) and already dumps the durable side well: the raw `last_addr`, the
parsed and relay-sanitized `hint_addrs`, `hint_usable`, `paired_at`, and the live reachability row
read straight from the cache so the diagnostic cannot perturb the reproduction it observes.

Adding a second verb over the top of that would have split one capture across two calls for no
reason. This is an extension.

Its doc also already carries the sharpest hypothesis anyone has produced for #140:

> "**But that lookup is skipped when a path is already selected.** iroh's `trigger_address_lookup`
> returns early if `selected_path.is_some()`, and a selected path is cleared only when the last
> connection to that peer closes. So on a pair that already holds an open RELAYED connection — live
> sessions, dial-backs, a working relay — discovery does NOT re-run, and this hint is the only
> addressing the dial contributes."

That would explain every observation in #140: why the failure is durable (the hint is on disk), why
it survives restarts and dial-backs (each re-establishes a relayed path that is then selected), and
why fresh identities punch in 23 ms (no hint, and discovery actually runs).

## The gap: we dump OUR state, never iroh's

Everything above describes what *this node stored*. Nothing shows what **iroh made of it** — and
that is the half where the hypothesis lives. A reporter can currently see a hint containing three
addresses and has no way to learn whether iroh holds those three, holds two of them plus a fourth
from discovery, or holds an entirely different set with a relay path selected.

iroh 1.0.3 exposes exactly this: `Endpoint::remote_info(id) -> Option<RemoteInfo>`, whose `addrs()`
yields each `TransportAddrInfo` with a `TransportAddrUsage` of `Active` or `Inactive`.

## What ships

Three additive fields on `PeerDiagnosticsResult`:

| field | meaning |
|---|---|
| `known_addrs` | `Option<Vec<KnownAddr>>` — every address **iroh** holds for this endpoint, each with `active`. `None` when iroh has no entry at all. |
| `hint_addrs_unknown_to_iroh` | addresses in our stored hint that iroh does not currently hold. **Not** accumulated cruft — the gate checked, and `set_last_addr` REPLACES the stored value wholesale with one built from the live connection's open paths. The draft repeated the issue's "amends but never removes" guess as fact in four places. |
| `iroh_addrs_not_in_hint` | the converse: what iroh knows that our hint never had |

`active` is **one bit covering three iroh states**: only an open path is active, while "attempted
hole-punching and it failed", "not yet attempted", and "inactive" all render `false`. So it cannot
discriminate the selected-path hypothesis from an ordinary failed hole-punch — which is the opposite
diagnosis. The first cut's CLI asserted "this is the #140 shape" on that bit alone.

`KnownAddr { addr: String, active: bool }`, rendered by the **same** labelling `hint_addrs` uses
(IPs verbatim, relays as `relay <sanitized-url>`) — the two lists are meant to be read side by side,
and differently-formatted addresses would make a genuine difference look like a formatting one.

**`None` is not an empty list — and it does not mean "never heard of".** The gate caught that
reading: iroh reaps a remote's state ~60s after its last connection closes (`ACTOR_MAX_IDLE_TIMEOUT`),
so absent is the normal answer both for a peer never dialled and for one talked to minutes ago. On an
issue whose entire question is durability over time, "iroh has never heard of this peer" was the
worst available misreading, and the first cut printed it on the terminal.

**Both difference lists are empty when `known_addrs` is absent.** This was the gate's CRITICAL
finding: flattening `None` to an empty view put the whole hint into `hint_addrs_unknown_to_iroh`,
so the CLI — which auto-starts a daemon that has dialled nobody — printed "stale: 192.168.1.50:4433"
about a hint that was current and correct. A diagnostic that confidently mislabels the default case
is worse than no diagnostic.

**The two differences are computed rather than read.** iroh 1.0.3's `TransportAddrInfo` carries no
provenance, so "did this come from our hint or from discovery?" cannot be answered directly. Set
difference is an inference and is labelled as one; claiming a source we cannot read would be worse.

### Still read-only

`remote_info` is a point read of iroh's remote map: no dial, no probe, no address lookup, no
mutation. That much the gate verified against iroh's source.

**With one caveat it also found, which the draft glossed as "cannot perturb".** Delivering the
message resets that remote's ~60s actor idle timer, so polling this verb keeps remote state — a
selected path included — alive that would otherwise be reaped. The issue thread tells the reporter to
close every connection and confirm nothing holds a path; polling this while waiting would prevent
exactly that. Stated in the docs. The call is also bounded (`REMOTE_INFO_TIMEOUT`), since it awaits
an mpsc send and a oneshot with no timeout of its own while every other await in the handler is
bounded or cache-local.

## What this does NOT do

- **It does not fix #140, and the issue stays open.** Shipping an instrument and closing the bug it
  was built to investigate would be the wrong shape.
- **It does not prune the stale hint.** Pruning is the most plausible *fix* and it is still a guess:
  the reporter has run three releases of changes chosen without data. The next change to the dial
  path should be made after a capture, not before one.
- **It does not confirm the selected-path hypothesis.** That needs two machines on a real LAN, which
  cannot run in CI. It makes the hypothesis *checkable* by the people who have them.

---

## Testing

1. **The projection is pure and tested directly**: a hint address iroh does not know appears in
   `hint_addrs_unknown_to_iroh` and nowhere else; an iroh address absent from the hint appears in
   `iroh_addrs_not_in_hint` and nowhere else; an address in both appears in neither difference;
   `active` is carried per address, not collapsed.
2. **Absent and empty are distinct on the wire**: `None` elides the field, an empty `Vec` serializes
   as `[]`.
3. **Relay URLs are sanitized in `known_addrs` too**, asserted against a URL carrying a userinfo
   token — this output exists to be pasted into a public issue, and the existing `hint_addrs`
   sanitization would be pointless if its neighbour leaked the same token.
4. **End to end through the real control socket**, since the last three gates each found a dispatch
   arm that could be deleted with a green suite.

### Mutations to run

- either set difference reversed → `the_hint_and_iroh_differences_are_not_transposed` fails, AND the
  end-to-end assertion in `peer_diagnostics_reports_the_hint_the_dial_would_actually_use` fails.
  Both, deliberately: a pure-function test proves the helper, not the call site, and this repo has
  now shipped that exact gap twice (0.49.0's clock deltas, 0.49.1's hedge plan).
- `None` collapsed to an empty vec → the `known_addrs == None` assertion for a never-dialled peer
  fails.
- `known_addrs` relay labelling switched to `{:?}` or unsanitized →
  `a_relay_url_is_stripped_of_userinfo_wherever_it_is_labelled` fails.
- the labeller diverging between the two lists → the differences go wrong, because they are
  computed on the labelled strings; sharing one `label_transport_addr` is what makes the set
  difference meaningful at all.

**The draft declared this gap unavoidable and the gate proved otherwise** — by deleting the entire
`remote_info` call and watching all 420 tests pass. `known_addrs_reports_irohs_own_view_once_a_connection_exists`
now stands up two real endpoints, makes one real connection, and reads the verb: the deletion and a
hardcoded `active: false` both fail it. The dial is the TEST's, before the verb is called, which is
why it cannot live inside `peer_diagnostics_never_dials`.

That is the third time in one session this repo has shipped a thoroughly-tested helper whose call
site nothing reached.

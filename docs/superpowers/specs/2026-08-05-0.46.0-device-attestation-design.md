# 0.46.0 design — device attestation (#85 ask 3)

Version: **0.45.0 → 0.46.0 (MINOR)**. `API_MINOR` 51 → 52.

Closes #85.

---

## The gap

> **A device attestation signed by the UserKey** — `sign(user_key, new_eid)` — so a peer that
> already stored my `b64u:` admits a replacement device without a fresh SAS.

Everything needed to *verify* one already exists. `binding::present` signs it, `verify_presented`
checks it against the TLS-authenticated endpoint, and the pairing hello already carries
`user_pk` + `binding_sig`. What is missing is a node that will **act** on one: `PeerEntry.user_id`
is written once at pairing and never refreshed, and the gate refuses an endpoint with no row. So a
replacement machine holding the right user key — restored from 0.42.0's recovery phrase — is still a
complete stranger to every peer.

## The ceremony

A new device dials `mcpmesh/pair/1` with `attest: true` instead of a live invite secret. That ALPN
is already gate-exempt (its authentication is the invite secret, not the allowlist), already
rate-limited, and already binds every claim to `conn.remote_id()`. Reusing it means no second
gate-exempt surface, which is the property that makes this reviewable at all.

The receiving node then, in order:

1. **Verifies the binding against the TLS-authenticated endpoint id.** `verify_presented` yields the
   `user_id`; a transplanted binding for a different endpoint fails.
2. **Refuses a REVOKED endpoint** (0.45.0). Checked before anything else that could write.
3. **Requires an existing `PeerEntry` carrying that `user_id`.** This is the whole authorization: I
   admit another device of a person I already paired with. A `user_id` I have never seen is refused
   — attestation is not a pairing mechanism.
4. **Writes a row for the new endpoint**, same `user_id`, same nickname (it is the same person, and
   nicknames are per-person, not per-device), services = the **intersection** across that person's
   existing rows.
5. **Audits it and pushes a `subscribe` frame.** A device joining under a known identity is never
   silent.

### Intersection, not union

If Bob's laptop is granted `notes` and his phone `notes,files`, a new Bob device gets `notes`. A new
device must never arrive with more access than the least-privileged device the person already has;
the operator can widen it with `service_allow_grant`. Union would let someone with the user key
mint a device that inherits the most-privileged grant on the node.

## Opt-in, default OFF

`[identity].admit_attested_devices = false`.

This changes what a pairing *means*: today it admits a device, and with this on it admits a person
and their future devices. That is arguably what #38 already made true of grants — they are keyed on
stable principals, so a person's devices already share authorization — but "arguably implied" is not
a reason to widen admission on somebody's node during an upgrade. An embedder building a messaging
product turns it on; a person running a two-machine mesh may prefer to keep pairing explicit.

#85 asks for this to be seamless. It is one config line, and the reason it is not the default is
written down rather than left as an omission.

## What it deliberately does NOT do

**It does not resurrect a device you removed.** `peer_remove` deletes the row; it does not stop the
*person* from attesting a device afterwards, because you still pair with them. If you removed a
device because it was compromised, **revoke it** — attestation checks the revocation list first, and
that is precisely why ask 4 shipped before this.

That is a sharp edge, and it is put where an operator can see it: `peer_remove`'s docs say it, the
CLI says it, and the release notes say it. The alternative — tombstoning every removal — would make
the routine verb irreversible to fix a problem the compromise verb already solves.

**It does not let a stranger in.** Step 3 refuses a `user_id` with no existing row, so the worst a
holder of an unknown user key can do is spend a rate-limited connection.

**It does not widen who can speak for a person.** Anyone holding the user key can add devices under
that identity — but that key *is* the person; someone holding it can already present as them
anywhere. This adds no capability an attacker did not have.

## The cost: the pair ALPN's front door stays open

`spawn_accept_loop`'s `ALPN_PAIR` arm fast-closes when `invites.count() == 0`, which is what keeps
the by-design-open pair ALPN shut except during an invite window. An attestation needs no invite, so
with `admit_attested_devices` on that fast-close must be skipped and the ALPN is reachable
continuously.

Stated rather than buried: turning this on trades the invite-window bound for continuous
reachability of a rate-limited, binding-verified ceremony that can only ever admit a device of a
person you already pair with. With the knob off — the default — the fast-close behaves exactly as it
does today.

## Surface

No new control verb. The ceremony is mesh-side, and the *initiating* side already has one:
`mcpmesh pair <invite>` becomes `mcpmesh pair --attest <peer-address>`… except the new device needs
somewhere to dial. It has the peer's address only if it has a row for them — which, after a recovery
phrase import, it does not.

So the new device needs the peer's dialable address out of band, exactly as a first pairing does.
The honest surface is therefore an **attestation line**, minted by the peer that will admit you:

```
mcpmesh attest offer                 # on the peer: prints mcpmesh-attest:<addr+id>
mcpmesh attest <line>                # on the new device: runs the ceremony
```

`attest offer` mints nothing secret — the line carries only the offering node's id and address, both
of which an invite already carries in the clear. It exists so the new device knows where to dial.

`status.self_network` gains nothing; `status` gains nothing. The new row shows up in `peers` like
any other, which is the point.

## Testing

1. **The happy path, through two real nodes.** A pairs with B. B's user key is exported and imported
   on C (a third node). C attests to A and is admitted with B's `user_id`, B's nickname, and B's
   services — then opens a real MCP session, which is the property that matters.
2. **A stranger's user_id is refused** — C attests with a user key A has never seen.
3. **A revoked endpoint is refused**, even with a valid binding to a known person. This is the
   ask-4 interlock and the reason for the ordering.
4. **A forged binding is refused**: a binding signed for a *different* endpoint, presented by this
   one.
5. **Off by default**: the same ceremony against a node that has not opted in is refused, and the
   pair ALPN's fast-close still behaves as it does today.
6. **Services are the intersection**, not the union, across the person's existing rows.

### Mutations to run

- the `user_id`-must-exist check removed → the stranger test fails.
- the revocation check removed → the revoked test fails.
- `verify_presented` given the claimed id instead of the TLS id → the forged-binding test fails.
- intersection replaced with union → the services test fails.
- the opt-in ignored → the default-off test fails.

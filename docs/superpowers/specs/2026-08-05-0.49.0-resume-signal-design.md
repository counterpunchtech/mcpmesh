# 0.49.0 design — a resume signal (#167 ask 2)

Version: **0.48.0 → 0.49.0 (MINOR)**. `API_MINOR` 54 → 55.

---

## The gap

> **Is there a resume/suspend signal an embedder can hook, so an app can tear down and re-dial
> deliberately rather than discover it on the next send?**

#167 asks three things. Two were answered in 0.40.0 by documenting them: `open_session` does not
re-establish (the client sees EOF), and `subscribe` terminates with the connection and does not
replay. This is the third, and it is the only one that needs code.

Today an embedder learns its session died by **trying to use it**. For a messaging app holding one
session per peer across a closed laptop lid — the reporter's steady state, not an edge case — that
means the failure surfaces when the user sends a message, which is the worst possible moment.

## Why a suspend is detectable at all

Rust's `Instant` is `CLOCK_MONOTONIC` on Linux and `CLOCK_UPTIME_RAW` on Apple targets, and
**neither advances while the machine is suspended**. The wall clock does. (An earlier draft said
`mach_absolute_time`; std's own comment notes `CLOCK_UPTIME_RAW` is identical to it, so the
behaviour claim held and only the API name was stale.)

So a ticker that measures both deltas tells the two apart:

| | monotonic Δ | wall-clock Δ |
|---|---|---|
| normal tick | ≈ period | ≈ period |
| **suspend/resume** | ≈ period | **≫ period** |
| CPU starvation / a stalled runtime | ≫ period | ≫ period |

A suspend is precisely "wall clock advanced far more than monotonic did". That distinction is what
keeps a loaded machine from emitting a false resume — which matters, because this repo has twice
produced confident-and-wrong diagnoses from single timing samples, and a signal that cried wolf
under load would be worse than none.

## What ships

A `StreamFrame::Resumed { suspended_secs, at_epoch }` on `subscribe`.

- Emitted **once per resume**, when the wall-clock delta exceeds the monotonic delta by more than a
  threshold.
- `suspended_secs` is the gap the machine was away — the number an embedder actually wants, because
  it decides whether to re-dial everything or nothing.
- Not retroactive: a subscriber that connects after a resume does not see it. This is a transition
  signal, like `Reachability` and `SelfNetwork` — but **unlike** those two there is no `Snapshot`
  field to recover a missed one from, because "was this machine recently asleep" is not state the
  daemon keeps. An earlier draft of this line said "the snapshot answers what is true now", which is
  true of the other two and false here.

**It says nothing about any particular session.** It cannot: the daemon does not know which of an
embedder's sessions still work, and a peer's connection may well have survived a short suspend. The
frame means "this machine was away for N seconds; check what you hold", which is exactly the
deliberate teardown-and-re-dial the issue asks for.

### The two deltas are ONE argument, not two

`detect_suspend`/`tick` take a `ClockDeltas { mono_secs, wall_secs }` struct rather than two `i64`s.
The rule is a subtraction of one from the other, so transposing them at the call site inverts it —
and the only production call site is a watcher loop no test can drive. The gate proved the cost
exactly: with the two arguments swapped, the feature is 100% dead in production (the skew goes
strongly negative on a real suspend, so nothing ever emits) and the entire workspace stays green.
Named fields make the wrong pairing something you have to write out deliberately.

### Threshold

`RESUME_THRESHOLD_SECS = 10`, against a 5s tick.

Above the tick by enough that ordinary scheduling jitter, a slow fsync, or a busy runtime cannot
reach it; well below the 30s default idle timeout, so the signal arrives for suspends that actually
kill sessions. A 3-second lid close does not fire, and nothing was lost either.

The tick was 2s in the first draft. The gate priced it correctly: this becomes the daemon's most
frequent periodic timer, on a feature whose entire audience is battery-powered laptops, and the cost
that matters is the WAKEUP defeating deep idle — not the two clock reads.

### It does NOT invalidate the reachability cache — checked, and it would be dead code

The first plan had the resume also clear the probe cache, so `status` could not serve pre-suspend
verdicts. **That was wrong, and reading the code is what showed it.** `ReachEntry.probed_at` is a
wall-clock epoch and `REACH_TTL_SECS` is 20, so an entry probed before a suspend of any length worth
signalling is *already* stale on resume and already re-probed. A `clear()` would change observable
behaviour only for a suspend between 10 and 20 seconds, and the test asserting it would pass whether
or not the line existed for every other duration.

Shipping it would have meant a doc claiming "the resume frame guarantees a fresh peer list" whose
real mechanism was a TTL that predates it.

## What this deliberately does NOT do

- **No transparent resumption.** `open_session` still does not re-establish, and 0.40.0's docs say
  so. Making it transparent means owning retry policy, backoff and idempotency on behalf of every
  embedder — a much larger change the issue does not ask for.
- **No replay.** `subscribe` still does not replay missed events; the frame tells you that you
  missed some, which is the honest half.
- **No suspend (pre-sleep) signal.** A process gets no reliable warning before suspension on either
  platform without OS-specific hooks; promising one would be a lie.

## Testing

1. **The detector is pure and exhaustively tested**: a normal tick emits nothing; a wall-clock jump
   with a normal monotonic delta emits; a jump in BOTH (CPU starvation) emits nothing; the threshold
   boundary is pinned from both sides.
2. **The frame reaches a subscriber** end to end, through the real control socket.
3. **Wire shape**: tagged `resumed`, both fields exactly as named, round-trips.

**A correction to an earlier draft of this line, found by the gate.** It said there was nothing to
assert about compatibility because `StreamFrame` is `#[non_exhaustive]`. That reasons about the wrong
language: `#[non_exhaustive]` is a Rust-`match` property and does **nothing** for serde. The enum is
`#[serde(tag = "type")]` with no catch-all, so a consumer pinned to `mcpmesh-local-api` 0.48.0 that
subscribes to a 0.49.0 daemon gets `ClientError::Malformed` on the first `resumed` frame and loses
the entire stream — at exactly the moment this feature exists to help. That is a genuine downstream
break, and it is the honest reason this release is a MINOR.

It is not "fixed" by tolerating unknown tags: `unknown_stream_frame_type_is_rejected` shows strict
parsing is deliberate, and the crates ship in lockstep for this reason. What ships instead is the
truth, in the three places that asserted otherwise — `StreamFrame`'s own rustdoc claimed additions
were "additive for Rust as well as for JSON", and `examples/watch.rs` claimed its `other` arm ignored
unknown frames "as the documented contract" when that arm cannot be reached for an unknown tag at
all.

### Mutations to run

- the monotonic delta ignored (wall-clock only) → the starvation test fails.
- the threshold comparison inverted or removed → the normal-tick test fails.
- the frame built but never sent → the end-to-end test fails.
- the subscribe mapping returning `None` → the end-to-end test fails.
- the CLI render arm deleted → the render test fails.
- the duration ladder collapsed to one arm, or a boundary moved → the band assertions fail.

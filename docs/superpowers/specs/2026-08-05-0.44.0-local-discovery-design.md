# 0.44.0 design — in-tree local (mDNS) discovery (#68)

Version: **0.43.0 → 0.44.0 (MINOR)**. `API_MINOR` 49 → 50.

MINOR: `SelfNetwork` (a `pub` struct in the published `local-api`) gains a field, and a node
configured for local discovery behaves differently on the wire.

---

## The gap

Peer resolution depends on external infrastructure — the pkarr publisher/resolver a relay provides,
or an address someone already handed over in an invite. Two machines on the same LAN with no
internet cannot find each other, though the network path between them is fine.

0.41.0 shipped the **seam** (`Node::add_address_lookup`), which unblocked writing a resolver outside
the crate. #68 stayed open for the resolver itself, which the issue calls "what most users would
want on by default".

## The issue's central claim is out of date, and it changes the work

> "In iroh **1.0.3** `src/address_lookup/` contains exactly `dns.rs`, `memory.rs`, and `pkarr.rs`,
> and there is no mDNS or local-swarm feature. That existed in iroh 0.x and is not present here.
> So this is not a flag; it needs an implementation."

The first half is true and I repeated it in the 0.41.0 design doc. The conclusion is wrong. iroh 1.x
did not drop mDNS — it **moved it out of the core crate**, and says so in the module docs of the very
file the issue inspected (`iroh-1.0.3/src/address_lookup.rs`):

> mDNS-based and Mainline-DHT-based Address Lookup services live in separate crates:
> [`iroh-mdns-address-lookup`] and [`iroh-mainline-address-lookup`].

`iroh-mdns-address-lookup` 0.4.0 is published by n0, depends on `iroh ^1.0.0` (our exact pin), and
implements `AddressLookup` including the advertise side. So this is a **dependency plus wiring**, not
a protocol implementation.

That matters beyond saving effort: an mDNS implementation is a multicast responder on every
interface, and one written here would be ours to get right and ours to keep right. Taking n0's keeps
it version-matched to the transport it feeds.

Dependency cost, measured (`cargo add` → `Cargo.lock` diff): **four** new crates —
`iroh-mdns-address-lookup`, `swarm-discovery`, `acto`, `smol_str`. Everything else it needs
(`iroh-base`, `n0-future`, `n0-watcher`, `n0-error`, `data-encoding`, `derive_more`, `tokio-stream`,
`futures-util`, `tracing`) is already in the tree via iroh, and `swarm-discovery` is the same crate
iroh 0.x used for this.

## What ships

```toml
[network]
local_discovery = "off"       # default — no multicast, no listening
                = "on"        # resolve peers on the LAN AND advertise this node
                = "resolve"   # resolve without publishing this node's identity
```

A string, not a bool, matching `relay_mode`/`discovery_mode` — and because the two halves are
genuinely separable and have very different disclosure. An unknown value is a **startup error**, like
its siblings: a metadata-privacy knob must not silently revert.

**Parsed before the endpoint binds**, beside `presence_mode` and `validate_service_rates`, so a bad
value fails the boot without first binding sockets; registered after, via the 0.41.0 seam, because
the service needs the bound endpoint id. (The first version parsed it *after* the bind with a
comment claiming otherwise — caught by the gate.)

`MdnsAddressLookup::builder()` takes `.advertise(bool)`, which is the `"on"` / `"resolve"` split.
`build` takes the parsed `LocalDiscovery` rather than that bare bool, so hard-coding it needs a
struct that visibly disagrees with config — the gate mutated a bare bool to `true` and every
deterministic test stayed green.

`status.self_network` gains `local_discovery: String`, reporting the effective mode — so an operator
debugging "why can't these two find each other" can see it from the control API rather than from a
config file they may not be reading.

### Service name: `mcpmesh`, not n0's default

The crate defaults to `irohv1`, which is the **shared iroh namespace**: every iroh application on the
LAN advertising into it, and us into them. Discovery authorizes nothing — a peer found this way still
faces the trust gate — so cross-discovery is not a security problem. It is a disclosure and a noise
problem: our node would announce itself to unrelated iroh apps, and resolve endpoint ids that can
never be ours.

Records take the form `<endpoint-id>._mcpmesh._udp.local`.

### Default OFF — deliberately, and against the issue's preference

The issue asks for this "on by default". Shipping it off, because the two disclosures are not
comparable:

- **pkarr** (today's default) publishes a *signed record* that someone must already know your
  endpoint id to look up. It is a lookup table.
- **mDNS** announces your endpoint id and your addresses to **every device on the link**, unprompted
  and repeatedly, to machines that had no idea you existed. On a home LAN that is what you want. On a
  café, hotel, conference, or coworking network it is a broadcast of "this device is here, and here
  is its stable cryptographic identity" to strangers — and the same identity is the one peers pin, so
  it correlates you across networks.

A node cannot un-send a multicast packet. Turning this on is one line of config and reversible;
turning it on for someone silently is not. `"resolve"` exists so a person who wants the benefit
without publishing their identity has that.

**`"resolve"` is quieter, not silent**, and the first version of this document said otherwise.
`MdnsAddressLookup` builds a `Discoverer::new_interactive` **unconditionally** (τ = 700 ms) and
`advertise` gates only `with_addrs` — so a resolving node multicasts a `_mcpmesh._udp.local` query
about once a second, forever. No identity and no addresses go out (pinned on the wire), but the
query says "an mcpmesh node is at this IP, right now". The gate captured the packets.

That also cuts against the service-name reasoning above: `mcpmesh` makes the query *more*
identifying than `irohv1`. The trade stands — blending into unrelated traffic is not a privacy
property to rely on, and the `"on"` path is where identity actually leaks — but it is a trade, not
a free win.

This is a deliberate departure from the ask and is called out in the release notes and on the issue,
not buried.

### What is actually multicast

This node's endpoint id, its direct addresses, and its relay URL if it has one. "Direct addresses"
is broader than it sounds: the gate decoded a real announcement and it carries the **LAN address,
the public WAN IPv4, and global IPv6**. A café LAN learns your home/ISP address, not merely that you
are on that café's network.

**`relay_only` does not restrain any of this on a stock build**, and the first version of this
document claimed it did. `AddrFilter::relay_only()` is installed only under the
`unstable-relay-only` feature (`apply_relay_only`); without it, `relay_only = true` is inert — it
says so in its own docs — and the full direct set goes out. Boot warns per build, naming which of
the two the operator has, instead of printing a warning that contradicts the "relay_only is
IGNORED" line next to it.

`presence_mode = "off"` and advertising also work against each other: the first withholds
reachability from paired peers, the second broadcasts it to the whole link. Boot warns.

Stated plainly in `docs/config.md`, because "what does this send" is the question an operator
actually has.

## The issue's open question, answered

> Does a previously-resolved peer with a cached address still connect when resolution is
> unavailable?

**Yes, for a peer this node has already dialled** — and the first draft of this section said
otherwise. It repeated the 0.41.0 answer ("`dial_one` dials a bare id with no store read, so a
two-device person depends entirely on resolution"), which was true then and was **fixed by #186 in
0.41.1** — a release from this same maintainer run. Both racing paths now call `hinted_addrs`
(`node/src/daemon/dial.rs:67` and `:105`), which reads `store.resolve()` per candidate; the code
comment there names the exact scenario the draft claimed was still broken. Caught by the 0.44.0
gate, and recorded rather than quietly deleted, because repeating a stale finding about one's own
tree is the failure mode worth remembering.

So the honest answer: a peer with a stored `last_addr` still connects offline. What local discovery
adds is the case with **no** stored hint — a first contact on an air-gapped LAN, or a peer whose
address changed — which no cache can cover.

The remaining dial-hint gap is #140, and is separate.

The accept side of per-connection transport config (#166) and the roster/org-root work (#93c) are

## Testing

The hard part is that a real mDNS test needs multicast, and CI runners frequently block or isolate
it. The suite must therefore not *depend* on multicast working, while still proving the wiring.

1. **Config parse**: `"off"` / `"on"` / `"resolve"` map to the right (enabled, advertise) pair;
   absent is off; an unknown value is a **startup error**, not a silent default. Pinned both ways —
   this is the same class as `relay_mode`, where a silent fallback to public infrastructure would be
   a privacy failure.
2. **Boot wiring**, through `NodeBuilder` with a real `config.toml` — the gap the 0.43.0 gate found
   in #80, where a fully tested helper was joined to config by an unpinned line. `status.self_network
   .local_discovery` must report the configured mode, and `"off"` must register no lookup at all.
3. **Two real nodes on loopback**, both `relay_mode = "disabled"`, node b given only node a's `eid:`
   and no stored address — the same construction the 0.41.0 seam test used. Node b resolves a and
   connects. **Marked `#[ignore]` and run explicitly**, because multicast on a CI runner is not a
   property of this code. The seam itself is already covered by 0.41.0's `MemoryLookup` test, which
   is not ignored.
4. **`"resolve"` must not advertise.** Asserted through the builder's `advertise` flag reaching the
   service, since observing the absence of a multicast packet is not something a unit test can do
   honestly.

5. **On the wire**, `#[ignore]`d: a test that joins 224.0.0.251:5353 and reads the packets. `"on"`
   must put the endpoint id on the link under `_mcpmesh`; `"resolve"` must NEVER put the endpoint id
   on the link, and must still be seen querying. This exists because the gate proved nothing else
   could see either property — the crate exposes no way to read them back.

### Mutations to run

- `local_discovery` never read at boot → the boot test fails (the #80 lesson: pin the call site).
- `"resolve"` mapped to `advertise: true` in the parser → the mode test fails.
- an unknown value falling back to `"off"` instead of erroring → the config test fails.
- the service-name CONSTANT reverting to `irohv1` → the constant test fails.
- `.advertise(..)` hard-coded to `true` → **only the wire test fails**; it was invisible before.
- `.service_name(..)` deleted → **only the wire test fails**; both nodes fall into `irohv1`
  together, so even the connectivity test passes.

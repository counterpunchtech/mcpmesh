# 0.38.0 design — roster mode from an embedded node (#66, #93 a+b)

One theme, two issues that reference each other: **what would have to be true for an embedder to
adopt roster mode?** #66 covers the write side (authoring verbs); #93 covers everything else.

Version: **0.37.0 → 0.38.0 (MINOR)**. New control verbs, new public items in three published crates,
and a behaviour change (`org_join` now reports `restart_required`). `API_MINOR` 45 → 46.

---

## #93 (a) — the roster was unreadable over the control seam

The signed roster holds `display_name`, `groups`, and per-user devices. None of it crossed the seam:
`RosterStatus` was `{org_id, serial, state, fingerprint}` and `PresencePeer` dropped `display_name`
and `groups`. So an embedder in roster mode had managed group membership it could not display, and
the only route to a member list was hand-parsing `<root>/config/roster.json` — the daemon-owned read
the embedding contract exists to avoid.

### `roster_members`

```
{groups: […], users: [{user_id, display_name, groups: […],
                       devices: [{label, role, principal, online}]}]}
```

**It answers a different question from `status.presence`.** That projection enumerates reachable
DEVICES, so a person whose devices are all down appears nowhere in it. This is the member list;
`online` rides along per device so one read serves both.

Two decisions worth stating:

- **Devices carry their `eid:` principal**, where `PresencePeer` deliberately omits it. This surface
  exists to be *acted on* — granting or revoking one device of a person needs a handle to name it,
  and roster mode has no nicknames.
- **Seeded from the roster's USERS, not the device map.** Corrected during the adversarial gate; see
  below. The device map is keyed by endpoint because that is what the gate resolves, so a person
  whose devices are all revoked is absent from it.

Plus `display_name` + `groups` on `PresencePeer`, and `groups` on `RosterStatus` — so a UI can
populate a group picker from the same read that tells it a roster exists.

`RosterView` gains `users()` and `groups()` accessors and `ResolvedDevice` gains `display_name`.

## #93 (b) — `org_join` was half-live with no error

`roster_mode` is a **boot-time snapshot**. It fixes the ALPN set bound on the endpoint and whether
gossip, presence and app-blobs are constructed at all. The roster **gate**, by contrast, hot-swaps.

So a node that booted in pairing mode and then ran `org_join` reached a state where MCP sessions to
org members started working while `status.presence` stayed permanently empty and every blob verb
hard-closed with `blobs not enabled`. It succeeded, partially, with no error anywhere.

`OrgJoinResult.restart_required` — the `{changed, restart_required}` shape #53 established.

**Derived from whether the transport is actually composed (`gossip.is_some()`), not from
`roster_mode`.** They differ in a case that matters: `compose_roster_transport` also returns nothing
when roster mode is on but no `org_id` is known. The ALPNs bind, presence still does not work, and
`roster_mode` would report "live" for a node that is not.

## #93 (c) — org root rotation: NOT in this release

Needs its own design. An operator machine that dies still takes the org with it once the roster
expires. Stated in the `api_minor` 46 ledger entry and in `docs/embedding.md` rather than left
implied, with the workaround (back up `org-root.key` alongside `roster.json`) documented.

## #66 — org authoring as control verbs

`Request` carried `roster_install` and `org_join`, both CONSUMER verbs. An embedder that wanted
managed group membership had to shell out to the `mcpmesh` binary — a second artifact to ship and
version-match, and the enrollment UX reproduced in a terminal beside its own UI. Concretely: no
"approve this person" button.

New verbs in `node/src/daemon/org_author.rs`:

| Verb | Notes |
|---|---|
| `org_create` | Mint the root, sign an empty roster, install it (pinning the root). **One-time per node** — a second call is refused rather than replacing the key, which would orphan every roster already signed. |
| `org_join_code` | **Added during the gate.** Inspect a code without approving it. Read-only. |
| `org_approve` | Verify the binding **before** any roster access, upsert, bump, re-sign, install. |
| `org_revoke` | Three-way target grammar, reporting which `mode` it applied. |

`cli/src/enrollcmd.rs` now CALLS these; `load_operator_roster` and `install_signed_roster` are
deleted from it. They were a second copy of the same logic, free to drift.

### What moved, and what did not

The org root key stays at `<config_dir>/org-root.key`, derived from `mesh.config_path` exactly as
`installed_roster_path` derives `roster.json`, so a `--profile` root and an embedded node each keep
their own. The daemon runs as the caller's uid and the socket is same-uid gated (`ipc.rs` checks
`peer_cred()` against `geteuid()`; the dir is 0700, the socket 0600), so anything that can reach the
socket could already read the key. What changes is that it is read by the process that already owns
every other piece of durable trust state.

An authored roster installs through the **same** convergence path gossip and the URL poll use, so it
is validated, persisted, hot-swapped, severed and audited identically.

The HUMAN half does not move and cannot: verifying that a join code came from the person you think
it did is an out-of-band conversation.

## Changed by the adversarial gate

Run against the committed diff before the branch was pushed. Two findings were proven by execution.

1. **A `/` in a `user_id` hijacked the revoke grammar.** `org_approve` took `requested_user_id`
   straight from the join code — a value the person *being approved* chooses. Approving
   `alice/laptop` meant a later `org_revoke("alice/laptop")` parsed as "alice's laptop device": the
   operator trying to remove the hostile entry cut the real Alice's laptop and left the hostile user
   in the roster, with `mode: "device"` and a confirmation sentence that reads correct for both
   intents.

   Worse, the first version had added exactly this guard to the *org name*, which is never a revoke
   target, and omitted it from the field that collides. Now refused at approval, where the namespace
   is decided; device labels may still contain `/`, which stays unambiguous once no `user_id` does.

2. **`roster_members` silently dropped a member with zero active devices.** Building it from the
   device map omitted anyone whose devices were all revoked — the *designed* outcome of
   `org_revoke <user>/<device>` on someone's only machine, which leaves their user entry in the
   signed roster. It contradicted this design's own "every person the roster carries" contract.
   Now seeded from `RosterView::users()`.

3. **The authoring read-modify-write was outside any lock.** Two concurrent `org_approve`s (legal
   since #172's concurrent dispatch) both read serial N; the loser failed with a roster-rollback
   validation sentence, an opaque answer for an approve button. Now serialized by
   `MeshState::org_author_lock` — a separate lock, because `install_roster` takes `reload_lock`
   itself and tokio's `Mutex` is not reentrant. Ordering is authoring → `reload_lock`, never the
   reverse.

4. **An embedder could not run the ceremony this issue exists for.** The fingerprint was only on
   `OrgApproveResult` — i.e. *after* install — and `JoinCode` lives in `mcpmesh-node`, not on the
   control seam. So the doc telling operators to confirm it "before trusting the approval" described
   something the API did not make possible for its stated consumer. `org_join_code` added; the CLI
   now routes its own pre-install confirmation through it, so both compute the words one way.

5. **Two integration assertions had gone vacuous.** `staged_temps` scanned for `roster.staging.*`,
   a prefix the deleted CLI helper wrote — including the assertion whose whole purpose is
   "the guard removes it on the install-ERROR path". Fixed, and the staging file moved from the
   shared system temp dir to the node's own config dir: per-node state, same argument as
   `installed_roster_path`, and a shared dir made one node's in-flight file indistinguishable from
   another's leak (it made these tests cross-talk under parallel execution).

6. **`org_create` could fail after the org existed.** `expires_secs` was validated *after* the key
   was minted, and a `set_roster_url` failure returned `Err` — with the one-time guard then refusing
   the retry. Every cheap check now runs before the key is persisted, and the URL pin is
   best-effort (the org exists; the URL is a convenience `set_roster_url` can fix).

7. Smaller: `user_key: true` with a device-shaped target is refused by name rather than reported as
   a missing person; the CLI's unknown-`mode` fallback prints the mode verbatim instead of the most
   destructive of the three sentences; the `org_join` docs row documents `restart_required`.

## Testing

Every property mutation-tested — break it, watch the named test fail, restore.

**#93**: revoked-device exclusion removed; members built from the presence table; `display_name`/
`groups` dropped from the presence projection; `RosterStatus.groups` emptied; `restart_required`
hardcoded each way; `roster_transport_live` inverted; members seeded from devices again (the gate
finding); the device sort deleted.

The `roster_members` fixture was strengthened after the gate showed the sort was unpinned: Alice now
has two ACTIVE devices listed mirror-first with a label that sorts before the primary's, so document
order, label order and role order all disagree. A third member sorts last by `user_id` and first by
`display_name`, pinning the ordering key against a rename reshuffling the list — and their only
device is revoked, pinning finding 2.

**#66**: rotation revoking the devices (locks the person out of their own laptop); departure leaving
them usable; the one-time `org_create` guard removed; the binding check moved after the operator
load; the `/` guard removed (reproduces the exploit); the rotation grammar guard removed;
`org_join_code` and `org_approve` computing separate fingerprints; the staging guard leaked.

Two tests were found vacuous by mutation rather than by review:

- The second `org_create` asserted only `is_err()` — and without the guard it still fails, on the
  roster serial check, for a reason unrelated to the orphaned root that would already have happened.
- `staged_temps`, above.

# 0.41.0 design — an embedder seam for peer discovery (#68, the smaller option)

Version: **0.40.1 → 0.41.0 (MINOR)** — a new public item on `mcpmesh-node`. No control verbs, no
`api_minor` bump.

---

## The gap

Peer resolution depends on external infrastructure: the pkarr publisher/resolver a relay provides,
or a dialable address someone already handed over in an invite. Two machines on the same LAN with no
internet cannot find each other, though the network path between them is fine.

That is the scenario where "peer to peer" earns its keep — a boat, a workshop, a failed uplink, a
deliberately air-gapped network — and the weaker, commoner one too: a LAN where the internet is
merely flaky, so peers that could talk directly fail to resolve because resolution goes out first.

## Why not just switch mDNS on

The issue is precise about this and it checks out: in iroh **1.0.3** `src/address_lookup/` contains
exactly `dns.rs`, `memory.rs`, and `pkarr.rs`, and there is no mDNS or local-swarm feature. That
existed in iroh 0.x and is not present here. So this is not a flag; it needs an implementation.

## What ships

The issue offers two answers and says the second "is smaller and unblocks experimentation". That is
the one here:

```rust
impl Node {
    pub fn add_address_lookup(&self, lookup: impl iroh::address_lookup::AddressLookup + 'static)
        -> anyhow::Result<()>;
}
```

`AddressLookup` is a public, pluggable trait, so an mDNS implementation — or any other — can live
outside this crate. Both its methods have defaults, so a minimal implementation is small.

**Runtime, not builder.** `Endpoint::address_lookup().add()` exists, so registration works on a
running node, consistent with `accept_protocol` (#67). Documented limit: a dial already in flight is
not re-resolved.

## It publishes as well as resolves

Found by the gate, and measured: iroh hands the service this node's `EndpointData` — LAN IP, public
WAN IP, global IPv6 — synchronously inside `add`, and again on every address change. The first
version of this seam called it "a peer RESOLVER" and never mentioned publication, which is a
disclosure an embedder would not expect from that name. Now stated first in every doc site.

The node's address filter is *not* bypassed: it runs centrally in `AddressLookupServices::publish`
before any service sees the data, so a relay-only posture hands over relay-only addresses.

## Two properties

- **Additive, never authoritative.** The lookup is consulted alongside whatever the node already
  has; adding one cannot remove relay-based resolution.
- **Resolution authorizes nothing.** A peer found this way faces the trust gate exactly as one found
  any other way — resolution answers *where*, never *who may*. This is what makes the seam safe to
  hand an embedder at all: a resolver cannot widen who the node admits.

## Not in this release

An in-tree mDNS implementation behind `[network].local_discovery`, which the issue says "is what
most users would want on by default". #68 stays open for it. This is the seam that unblocks writing
one outside; it is not the discovery.

Also unanswered, and worth carrying to whoever does the mDNS work — the issue's own open question:
does a previously-resolved peer with a cached address still connect when resolution is unavailable?

The honest answer is **partly, and less than it looks**, corrected by the gate. mcpmesh stores a
`last_addr` dial hint per peer, but does not attach it on every dial: `dial_one` — which every
RACING path goes through, the roster person→device race and the multi-device `user_id` race — dials
a bare id with no store read. The hint is attached only on the single-nickname fallback,
`dial_by_eid`, `connect_protocol`, and the reachability probe. So a person with two paired devices
under one `user_id`, on a LAN with no internet, depends entirely on resolution. Worth measuring
rather than asserting, and worth fixing on its own if it matters.

## Testing

Through two real nodes, both on `relay_mode = "disabled"` — no relay, no discovery — with node b
given only node a's `eid:` identity and no stored address. That is the air-gapped-LAN state the
issue describes, constructed rather than simulated.

1. **Before** the lookup is added, the dial fails: nothing can turn that identity into an address.
   This control is what makes step 2 mean anything — without it the test would pass on a node that
   had cached the address from an earlier dial.
2. **After** it, the same dial connects, resolved by the embedder's lookup and nothing else.
3. A SECOND lookup is added afterwards, and resolution still works — so `add` appends rather than
   replaces. Added after the gate observed that "additive" was asserted nowhere: both nodes are
   hermetic and start with zero lookups, so nothing could have been shadowed and no assertion would
   have failed if `add` replaced the list.
4. And the connection is closed `401` by a's gate, because b never paired with it.

Step 4 is context rather than evidence for THIS diff — it exercises #67's gate, and no mutation of
`add_address_lookup` can affect it. Recorded as such rather than counted.

A `MemoryLookup` stands in for the mDNS an embedder would write: what is under test is the seam, not
the protocol behind it.

Mutation caught: `add_address_lookup` made a no-op (step 2 fails, with a cause chain naming
"No address lookup configured" — which also confirms the step-1 control fails for the resolution
reason and nothing else).

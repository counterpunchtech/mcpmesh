# 0.45.0 design — pairing-mode revocation (#85 ask 4)

Version: **0.44.0 → 0.45.0 (MINOR)**. `API_MINOR` 50 → 51.

MINOR: new control verbs, a new durable table, and a behavior change at the trust gate.

---

## The gap

> **(c) Pairing mode has no revocation.** `revoked_endpoints` is roster-only. In pairing mode the
> only remedy is each peer independently running `peer_remove`, with nothing telling them they
> should. Until the last one does, whoever holds the disk authenticates as me, and every message
> they send is cryptographically indistinguishable from mine.

That is exactly right. `RosterGate::is_revoked` reads the signed roster's `revoked_endpoints`;
`AllowlistGate` has no equivalent, and `ComposedGate` asks only the roster. A pairing-mode node has
no way to say "this endpoint is dead" and no way to *tell anyone else*.

## Why this ships before ask 3, not with it

#85 ask 3 is device attestation: a peer that already holds my `b64u:` admits a replacement device
without a fresh SAS. It is the more visible half, and it is **unsafe without this one**.

Auto-admitting a device on the strength of a user-key signature means the holder of a user key can
put devices into other people's allowlists. If a peer removes a compromised device and that device
can re-admit itself by presenting a binding it still holds, `peer_remove` becomes decorative — the
one remedy pairing mode has today would be silently undone by the feature meant to improve it.

So revocation lands first, with the gate integration ask 3 will need, and ask 3 builds on it in
0.46.0. Stated on the issue rather than left as sequencing trivia.

## Two different acts, deliberately not one verb

The issue asks for "a revocation list so a compromised endpoint can be marked dead". There are two
directions, and conflating them would be a mistake:

| | Who decides | What it means | Who it protects |
|---|---|---|---|
| `peer_revoke` | **me**, about *your* device | "I no longer trust this endpoint" | me, from you |
| `device_revoke` | **you**, about *your own* device | "my laptop was stolen; stop trusting it" | you, from whoever holds your disk |

Local-only revocation solves the first and **not the second** — which is the one #85 is about. My
laptop being stolen is not something my peers can discover by themselves; I have to tell them, and
they have to be able to verify that it was me telling them. So the signed half is essential, not a
nice-to-have.

### `peer_revoke` / `peer_unrevoke` — local

Marks an endpoint dead in this node's own state. Not derived from `peer_remove`, deliberately:
removal is routine ("we are not working together any more") and re-pairing afterwards is normal;
revocation is a claim about compromise. Making them one verb would either make removal
irreversible or make revocation weak. They compose — a revoked endpoint stays revoked whether or
not a pair row exists.

Reversible (`peer_unrevoke`), because a local operator mistake must be fixable and this list is not
authoritative for anyone else. Both directions are audited.

### `device_revoke` / `device_revocation_import` — portable and signed

`device_revoke` signs, with **my user key**, a statement naming one of my own endpoint ids:

```
domain ∥ user_pk ∥ revoked_endpoint_id ∥ issued_at
```

A new domain, `mcpmesh/device-revocation/1`, separate from `mcpmesh/join/device-binding/1` and
`mcpmesh/introduce/1` for the same reason those are separate from each other: without separation a
device binding — which is signed over `domain ∥ user_pk ∥ endpoint_id`, the same shape — would
verify as a revocation of that device. That is not a hypothetical; it is the identical field layout.

`issued_at` is in the signed bytes so a later revocation cannot be replaced by replaying an earlier
one, and so an importer can order two statements about the same endpoint.

`device_revocation_import` verifies it and applies it **only if the importer already trusts that
`user_id`** — i.e. has at least one paired entry carrying it. A revocation signed by a stranger is
refused. That is what keeps this from being an unauthenticated "mark any endpoint dead" primitive:
the signer can only revoke devices of the person the importer already paired with, and can only
revoke *their own*, because the endpoint has to be bound to the signing user key… except it does
not, and that is worth being precise about.

**What the signature actually proves, stated exactly.** It proves the holder of `user_pk` asked for
`endpoint_id` to be treated as dead. It does **not** prove that `endpoint_id` was ever bound to
`user_pk`. So a peer could sign a revocation naming *someone else's* endpoint, and an importer who
trusts them would apply it.

Three ways to handle that; taking the second:

1. Ignore it. A paired peer can already refuse to talk to you; letting them mark a third party dead
   in your node is a different and worse power.
2. **Require the revoked endpoint to be one this importer associates with the signer's `user_id`** —
   i.e. `entries_for_user(user_id)` contains it, or the endpoint is unknown to us entirely (in which
   case the record is inert but recorded, so a later pairing with that endpoint is refused). This
   bounds the primitive to "you may kill your own devices in my node", which is exactly the ask.
3. Carry the original binding alongside, so the importer can verify the endpoint really was that
   person's. Strictly better cryptographically, and it fails for the case that matters: a device
   whose binding I never saw is precisely the one I have no row for.

Option 2 it is, and the residual is documented: an attacker who compromises a peer's user key can
revoke that peer's own devices in my node. They can already impersonate that peer entirely, so this
adds nothing to their power.

## Distribution is out of band, and says so

Pairing mode has no gossip. A revocation token is a string; getting it to your peers is the same
problem as getting them an invite line, and it is solved the same way — you send it to them. The
CLI prints it; `device_revocation_import` takes it.

Not pretending otherwise is the point. 0.46.0's attestation ceremony is the natural carrier, and
that is where automatic propagation belongs.

## Enforcement, and what it reuses

Almost nothing new. `TrustGate` already has `is_revoked` and `should_sever_now`, and #54 already
built the immediate-severance path (`register_checked` closes the TOCTOU race on a connection that
registers after the decision).

- `AllowlistGate::resolve` → `None` for a revoked endpoint. **Revocation wins over a pair row**,
  matching the roster gate's rule 1.
- `AllowlistGate::is_revoked` / `should_sever_now` → true.
- `ComposedGate` currently delegates all three to the roster alone. It must **OR** the two, or a
  roster-mode node silently loses pairing revocation.
- Revoking severs live connections immediately, like `service_allow_revoke` — a revocation that
  waited for the peer to disconnect would be unbounded, which is the #54 finding.

## Surface

| Verb | Params | Result |
|---|---|---|
| `peer_revoke` | `{peer, reason?}` — nickname, `eid:`, or `b64u:` | `{revoked: [principal], severed: n}` |
| `peer_unrevoke` | `{peer}` | `{unrevoked: bool}` |
| `device_revoke` | `{endpoint_id, reason?}` | `{token, endpoint_id}` |
| `device_revocation_import` | `{token}` | `{endpoint_id, user_id, applied: bool, severed: n}` |

`b64u:` on `peer_revoke` revokes **every** endpoint that node associates with that person — the
"I no longer trust this person, on any of their devices" case, which per-endpoint revocation cannot
express and which an operator will otherwise get wrong by doing it device by device.

`status` gains `revoked: Vec<RevokedEndpoint>` — `{principal, revoked_at_epoch, reason, source}`,
where `source` is `"local"` or `"signed"`. Without it the list is invisible and an operator cannot
tell why a peer is failing.

## Durable state

New redb table `revoked`: key = 32-byte endpoint id, value = JSON
`{revoked_at, reason: Option<String>, source, signer_user_id: Option<String>, issued_at: Option<u64>}`.

Additive-only, like `PeerEntry` — every field beyond the first two is `#[serde(default)]`, because
a row that fails to deserialize on an older binary would fail **open** here, and this table exists
to fail closed. The store's corrupt-row handling already bounds that per operation; a revoked row
that cannot be read is treated as **revoked**, not as absent. That asymmetry is deliberate and is
the opposite of what `PeerStore::resolve` does for pair rows, where an unreadable row means "not
paired" — both directions fail closed for their own table.

## Not in this release

Ask 3 (attestation) — 0.46.0, on top of this. Ask 1 (the key-protection seam) shipped in 0.39.0 as
`NodeBuilder::device_key`. Ask 2 (recovery phrase) shipped in 0.42.0. So #85 closes with 0.46.0.

## Testing

1. **The gate**: a revoked endpoint resolves to `None` even with a live pair row; `is_revoked` and
   `should_sever_now` agree; unrevoking restores it. Through `ComposedGate` as well as
   `AllowlistGate`, because that is the composition a roster node uses and delegating to the roster
   alone is the mistake available here.
2. **Immediate severance**, end to end through two real nodes: a live MCP session is cut when the
   peer is revoked, and the next dial is refused. Not "eventually" — #54's contract.
3. **Signature domain separation, proved rather than asserted**: a device *binding* must NOT verify
   as a revocation, and a revocation must not verify as a binding. Same field layout, different
   domain — the exact confusion the domain exists to prevent.
4. **Import authorization**: a token signed by a stranger is refused; a token signed by a trusted
   peer naming a *third party's* endpoint is refused; a token naming the signer's own endpoint is
   applied. The middle case is the one that turns this from a scoped primitive into a weapon.
5. **`issued_at` ordering**: a stale token cannot un-revoke, and re-importing is idempotent.
6. **Persistence**: a revocation survives a restart. A revocation that evaporated would read as
   durable and silently revert — the same failure #107's withdrawal tombstone was designed against.
7. **`b64u:` fan-out** revokes every device of that person, and only those.

### Mutations to run

- `ComposedGate` delegating `is_revoked` to the roster only → the composed-gate test fails.
- `resolve` returning the pair row for a revoked endpoint → the precedence test fails.
- the revocation domain equal to the binding domain → the domain-separation test fails.
- the import's "endpoint belongs to the signer" check removed → the third-party test fails.
- an unreadable revoked row treated as absent → the fail-closed test fails.
- severance deferred to disconnect → the immediate-severance test fails.

# 0.40.0 design — multi-source blob fetch (#83 ask 2) + the reconnection contract (#167)

Version: **0.39.0 → 0.40.0 (MINOR)**. `API_MINOR` 46 → 47.

---

## #83 ask 2 — a fetch cannot survive the publisher going offline

Content addressing makes every recipient a potential source. The control API made that unusable: a
`BlobTicket` names **one** address, so `AppBlobs::fetch` dialled the publisher and nothing else.

The failure the issue describes is ordinary, not exotic: someone posts a file to a room of eight and
closes their laptop. Three peers already hold the complete, byte-identical blob. The remaining five
fail — because the only address anyone has points at the sleeping publisher.

Ask 1 (`blob_republish`) shipped at `api_minor` 18, so a recipient *can* become a source. It just
could not be **used** as one.

### The seam

`BlobFetchParams.from: Vec<String>` — additional sources, taking the same vocabulary `open_session`
takes: `eid:` device principals, `b64u:` user_ids, or paired nicknames. Naming a *person* offers
every device of theirs, via `dial::protocol_candidates` (the resolver #67 added).

```
blob_fetch { ticket, dest_path, from: ["bob", "eid:…"] }
```

CLI: `mcpmesh blob fetch <ticket> <dest> --from bob --from carol`.

### Order, and why

**The ticket's own address first, then `from` in the caller's order.** The publisher is the
authoritative source and a live one costs nothing; an offline one costs one dial timeout (the same
`DIAL_TIMEOUT` every other dial uses) before the first alternate is tried.

Not a parallel race. A race would open connections it then abandons, and every abandoned dial is
work on someone else's machine. Stated as a limitation rather than hidden: a caller listing five
alternates behind a dead publisher waits through the timeouts in turn.

### What an alternate can and cannot do

- **It cannot substitute content.** `store.remote().fetch(conn, hash)` verifies BLAKE3 against the
  hash from the ticket as bytes stream, whoever supplies them. A hostile alternate can fail; it
  cannot serve a different file.
- **It can refuse.** An alternate serves only hashes it has republished into a scope granting the
  caller, so an ungranted one answers a permission error and the fetch moves to the next source.

### Resolution happens before the fetch

`dial::blob_source_addrs` resolves every name up front, so a mistyped nickname is a clean error
rather than a silent skip discovered after the publisher has already timed out. A name resolving to
nobody is an error, not an empty contribution — otherwise a caller watches the fetch fail on the
offline publisher and never learns its fallback list was empty all along. Duplicates are dropped:
a device two named people share would otherwise be dialled twice for one timeout each.

### Also verified, not reimplemented: ask 3

`AppBlobs::ticket_for` already performs the bounded `RELAY_READY_TIMEOUT` + `endpoint.online()` wait
before minting, gated by the flag `boot` enables — the treatment the issue asked be copied from
`invite`. It landed under #105. Reported on the issue.

## #167 — a session does not survive a closed laptop lid

**Documentation, not code**, and labelled as such. The issue asks three questions and says the
honest short-term answer is "hold the session loosely and re-dial on failure" — but that nothing in
the docs says so. That is a real deliverable: an embedder currently has to discover the contract by
losing a session.

`docs/local-protocol.md` gains a section under Sessions stating:

- Why no `[network]` knob fixes it — a suspended process emits no PINGs, the peer's idle timer runs
  on regardless, and `idle_timeout_secs` is negotiated to the minimum of both peers, so surviving a
  lid close needs every peer raised in lockstep. Resume also often brings a new network, and iroh
  cannot migrate a connection the peer already closed.
- **The three answers.** `open_session` does not re-establish (the client sees EOF). There is no
  resume/suspend signal. `subscribe` terminates with the connection and does not replay — though
  `lagged` does report in-session loss, which is backpressure rather than a reconnect.
- The recommended shape, and that reachability is advisory so re-dialling an "unreachable" peer is
  legitimate.
- What is **not implemented**, named: transparent resumption, a resume signal, replay of missed
  events.

The issue stays open. Documenting a gap is not closing it.

## Testing

**#83 ask 2**, through three real endpoints and a hard shutdown:

1. A publisher serves a blob; a recipient fetches it, republishes into a scope of its own, and
   grants the caller.
2. The publisher's endpoint is **closed**.
3. **With no alternates the fetch fails** — the control. Without it, step 4 could be passing against
   a publisher that never actually went down.
4. With the recipient named as a source it succeeds, and the bytes BLAKE3-verify against the
   original — so the fallback served the *same* blob rather than merely something.

Mutations caught: alternates ignored (step 4 fails, reporting "tried 1 source"); the ticket's own
address dropped from the source list (the pre-existing single-source test fails, "tried 0 sources").

The protocol test pins that `from` reaches the wire **in order**, that an absent field reads as
empty rather than inventing sources, and that an empty list does not bloat the payload.

## Changed by the adversarial gate

Six findings; the first proven by execution and severe.

1. **The fallback only triggered on a failed DIAL.** The loop broke out the moment
   `endpoint.connect()` returned `Ok`, so everything after that — an accept-time 401, a request-time
   permission refusal, "I don't hold that hash", a mid-stream reset — was a hard error with live
   alternates untried. Four doc sites claimed the opposite ("an ungranted alternate answers a
   permission error and the fetch moves on"), and the tree's own existing test already records that
   a refusal is *post-connect*.

   That is not an edge case: it is the ordinary shape of the room this feature exists for, where
   some recipients republished and some did not. Restructured so each source gets a full
   dial-and-transfer attempt (`try_source`) and **every** failure falls through. The transfer is now
   bounded too (`SOURCE_TRANSFER_TIMEOUT`), because a source that accepts and then stalls would
   otherwise hold the fetch open forever.

   The `Started` frame fires once before the loop and the terminal frame once after it, so a
   subscriber sees one logical transfer rather than a Started/Aborted pair per failed source.

2. **`blob_source_addrs` had no coverage at all** — nothing called it outside the handler, and the
   acceptance test passed literal addresses, bypassing resolution. `Ok(vec![])`, a deleted typo
   guard and a deleted dedup all survived. Now pinned: nickname, `b64u:`, `eid:`, order, dedup,
   the unresolvable-name error, and the cap.

3. **`from` was documented in the wrong table column** — the prose landed in the *result* cell, so
   it read as a field of `BlobFetchResult` while the params column still said `{ticket, dest_path}`.

4. **Unbounded fan-out.** `from` was an unbounded `Vec`, each name expanding to every device of a
   person, each dialled sequentially at a 20s timeout — an unbounded wait holding one of the
   connection's in-flight slots. Now `MAX_BLOB_SOURCES = 32`, refused rather than truncated:
   dropping the tail would make a fetch fail while the source that had the blob sat unused.

5. **"Duplicates are dropped" was true only among alternates** — the ticket's own address was
   prepended without a dedup, so naming the publisher (natural, to reach their *other* devices) cost
   a second timeout on the same dead address. Now filtered.

6. Source ORDER was untested; the acceptance test now puts a deliberately-useless source ahead of
   the good one, so a fetch that only falls back on unreachable dials fails.

Confirmed sound: substitution is impossible (`ticket.hash()` comes from the caller's own ticket at
every step and no source-supplied value influences it); cancellation still covers the whole source
walk; the progress ring is unaffected; `b64u:` really does resolve for paired peers.

**Filed separately:** the review found a pre-existing defect in `FetchGuard` — `guard.finished` is
set on *both* arms of the `select!`, including the cancel arm, so an explicit `blob_fetch_cancel`
never emits the terminal `Aborted` frame its `Drop` comment says it covers. Byte-identical on `main`
and out of scope here.

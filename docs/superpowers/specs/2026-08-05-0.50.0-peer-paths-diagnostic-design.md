# 0.50.0 design — `peer_paths`, the per-peer hint/path dump (#140)

Version: **0.49.1 → 0.50.0 (MINOR)**. `API_MINOR` 55 → 56.

---

## What #140 actually asked for

Two machines on one LAN cannot hole-punch as a **long-lived pairing**, while the *same two machines
on the same network punch `direct` in ~23 ms with fresh identities*. Raw UDP works both ways. #124's
dial-hint refresh fixed a WAN peer on the same fleet at the same moment and did not touch this pair.
The failure survives live sessions in both directions, dial-backs in both directions, and multiple
daemon restarts.

The reporter's ask is not "fix it" — it is a question and an offer:

> "What state does a long-lived pairing carry that a fresh identity does not, that could durably
> prevent a punch while leaving relayed connectivity healthy? … **If there is a way to dump per-peer
> path/hint state for a pair, we can capture it on both ends of a live reproduction** — this fleet
> reproduces it on demand."

**That is shippable here and the diagnosis is not.** Reproducing needs two machines on a real LAN,
which cannot run headless in CI. Handing the people who *have* the hardware the instrument they
asked for is the whole contribution this change can honestly make.

## The answer to the question, from reading the code

A long-lived pairing carries exactly one thing a fresh identity does not: **`PeerEntry.last_addr`**,
a persisted `EndpointAddr` JSON blob in redb. `stored_dial_addr` (`node/src/daemon/dial.rs`) attaches
it to every dial when it parses and its embedded id matches the row.

Its doc makes a claim that is the crux of the reporter's hypothesis:

> "iroh merges provided direct addrs with whatever discovery resolves, so attaching the hint never
> narrows reachability."

If that is true, the hint is not the cause. If it is *not* — if a stale address set provided by us
can outrank, delay, or crowd out what discovery finds — then it is exactly the "durable state that a
refresh amends but never invalidates" the reporter guessed at. **This design does not settle that.**
It makes the inputs visible so a live reproduction can settle it.

Note also that #124 *amends* `last_addr` and never removes an address from it: a peer that moved
networks twice (which this one did, in the onset window) accumulates addresses that were valid then
and are dead now.

## Surface

```
peer_paths { peer? }          → { peers: [PeerPaths] }
mcpmesh peer paths [<peer>] [--json]
```

`peer` is the usual vocabulary (nickname / `eid:` / `b64u:`); absent means every paired peer.

Per peer:

| field | meaning |
|---|---|
| `principal` | the stable `eid:` device principal — never a nickname, since this output gets pasted into issues |
| `nickname` | local display name, if any |
| `stored_hint` | the parsed `last_addr`: `{ direct_addrs: [..], relay_url }`, or `null` if the row has none |
| `stored_hint_raw_invalid` | `true` when `last_addr` is present but does **not** parse or names a different id — the silent-degrade case `stored_dial_addr` handles by ignoring it |
| `known_addrs` | what **iroh** currently holds for this endpoint: `[{ addr, active }]`, from `Endpoint::remote_info()` |
| `hint_addrs_not_known` | addresses in the stored hint that iroh does **not** list — dead weight the refresh never removed |
| `known_addrs_not_in_hint` | the converse: what discovery found that the hint never had |

The last two are the whole point. They are cheap to compute and they turn "does a stale hint crowd
out discovery?" from a hypothesis into two lists a reporter can paste.

**`known_addrs` is absent (not empty) when iroh has no entry at all** — `remote_info` returns
`Option`, and "iroh has never heard of this peer" is a different finding from "iroh knows it and
lists nothing". Collapsing them would destroy the distinction the diagnostic exists for.

## What this deliberately does NOT do

- **It does not fix #140**, and the issue stays open. Shipping an instrument and closing the bug it
  was built to investigate would be the wrong shape entirely.
- **It does not expose an address SOURCE.** iroh 1.0.3's `TransportAddrInfo` carries the address and
  an `Active`/`Inactive` usage and no provenance, so "did this come from our hint or from
  discovery?" cannot be answered directly — which is exactly why `hint_addrs_not_known` and
  `known_addrs_not_in_hint` are computed by set difference instead. Claiming provenance we cannot
  read would be worse than the inference.
- **It does not invalidate or prune the hint.** Pruning is a plausible *fix*, and choosing one
  before the data exists is how #140 got three releases of shots in the dark.
- **It is read-only.** No dial, no probe, no mutation — so running it during a live reproduction
  cannot perturb the thing being measured. That matters more than usual here: a probe is itself a
  fresh dial, and the reporter has already eliminated the probe cache as a cause.

## Security

`principal` is an `eid:`, which `status` already exposes. Addresses are the same coordinates invites
embed. Relay URLs go through the existing `sanitize_relay_url` — operator relay URLs can carry
userinfo tokens, and this output is *designed to be pasted into a public issue*, which makes it the
highest-risk surface for that leak in the tree.

Owner-only, like every control verb: the control socket is the trust boundary.

## Testing

1. **The projection is pure and tested directly**: hint present and fully known; hint present with a
   dead address (`hint_addrs_not_known` names it); discovery-only address (`known_addrs_not_in_hint`
   names it); no hint at all; a hint that does not parse; a hint naming a **different** endpoint id
   (the case `stored_dial_addr` silently ignores, which must be *visible* here — an operator
   debugging a dial needs to know the hint is being discarded).
2. **`None` from `remote_info` is distinct from an empty list** on the wire.
3. **Relay URLs are sanitized**, asserted against a URL carrying userinfo.
4. **End to end through the real control socket**, since the last three gates all found dispatch
   arms that could be deleted with a green suite.

### Mutations to run

- either set difference computed backwards → the dead-address and discovery-only tests fail.
- `None` and empty collapsed → test 2 fails.
- sanitization dropped → test 3 fails.
- the dispatch arm deleted → test 4 fails.

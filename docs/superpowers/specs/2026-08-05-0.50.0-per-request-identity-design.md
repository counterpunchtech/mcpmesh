# 0.50.0 design — identity injection on every request (#45 ask 2)

Version: **0.49.2 → 0.50.0 (MINOR)**. No control-API change, so `API_MINOR` stays 56.

---

## Why this is startable while #45 stays gated

#45 carries an explicit **"⛔ BLOCKED — do not start yet"** banner naming three gates. Two have since
lifted (rmcp is stable at 3.1.1 and we ship on `=3.1.0`; the `2026-07-28` spec is final). The third —
**real ecosystem adoption** — has not, and it is not being jumped here.

What is being taken is one of #45's three asks, chosen because it is the only one that is *already*
a defect rather than preparation:

> **(2) Identity injection** — inject `_meta["mcpmesh/peer"]` (and keep stripping caller-forged
> reserved keys) on **every** forwarded request, not just the first, since there is no single
> handshake to anchor it to. This is the forge-proofing surface — it must remain authoritative
> per-request.

The other two are deliberately left:

- **Ask 1 (routing) needs no work at all**, and the issue's framing of it turns out to be wrong.
  `select_service` reads `/params/_meta/mcpmesh~1service` from whatever the session's first frame
  is — **it never inspects `method`**. A stateless first frame routes correctly today. Ask 1 asks
  whether routing should become *per-request* rather than per-session; that is a real design
  question (it would let one session address several services), it is not forced by vNext, and
  answering it before a counterparty exists is exactly what the ecosystem gate is for.
- **#49 (reverse-DNS key strings) stays blocked.** It is a coordinated wire change both peers must
  adopt together, and this does not touch the key names.

## The gap, and what it is not

Today `inject_peer` returns early unless `method == "initialize"`. So:

| | today |
|---|---|
| caller forges `mcpmesh/peer` on frame 1 | stripped (`select_service`) |
| caller forges it on frame 400 | stripped (`sanitize_caller_frame`, every frame, batch-descending) |
| backend learns the caller on an `initialize` first frame | yes |
| **backend learns the caller on a non-`initialize` first frame** | **no — nothing is injected** |

**This is fail-closed, not forgeable**, and saying so precisely matters: stripping already runs on
every frame, so a caller cannot supply an identity mcpmesh did not vouch for. The backend sees
*nothing* rather than something attacker-controlled. It is a functionality gap, and it would have
been a security gap if the strip had the same `initialize` condition — it does not.

Under `2026-07-28` there is no `initialize`, so the first frame is an ordinary request and a served
backend can no longer identify its caller at all.

## What ships

`inject_peer` injects into **every caller→backend frame carrying a `method`** — requests and
notifications alike — instead of only `initialize`.

Everything else is unchanged and load-bearing:

- **The strip still runs first**, so injection remains authoritative rather than merging with
  anything the caller sent. Order is the security property; it is not being touched.
- **Batches still descend**, depth-bounded, exactly as `strip_reserved_meta` does.
- **`params`/`_meta` are still created when absent**, so a parameterless request gains a well-formed
  object rather than a scalar being overwritten.

**Frames without a `method` are left alone.** A caller→backend *response* (to a server-initiated
request — #91's push direction) has `id` + `result`/`error` and no `params`; inventing a `params`
object on one would be malformed JSON-RPC. The existing `method`-presence check already gives this,
so the change is genuinely one condition narrowing to "has a method" from "is `initialize`".

### Why MINOR rather than PATCH

`RELEASING.md`: breaking bumps the minor, everything else the patch. A served backend now receives
`_meta["mcpmesh/peer"]` on requests where it previously saw none. A backend that validates its
params strictly — a `deny_unknown_fields` handler, a schema with `additionalProperties: false` — can
**reject** requests it used to accept. That is a break in the mesh↔backend contract even though no
signature moved and no control-API field changed, so it is a MINOR, and the release notes say so
plainly rather than describing it as purely additive.

## Testing

1. **A non-`initialize` first frame gets the identity.** The vNext shape, and the actual defect: a
   session whose first frame is `tools/call` must reach the backend carrying `mcpmesh/peer`.
2. **Every LATER frame gets it too**, not just the first — the per-request authority the ask names.
3. **A forged `mcpmesh/peer` is replaced, not merged**, on a non-`initialize` frame. This is the
   ordering property; a test that only checks presence would pass on an implementation that injects
   *before* stripping and therefore ships the caller's value.
4. **A response frame is untouched** — no `params` invented on a frame that has no `method`.
5. **Batches**: every element with a `method` is injected, depth-bounded.
6. **The legacy path is unchanged**: an `initialize` first frame behaves exactly as before.

### Mutations to run

- the injection restricted back to `initialize` → tests 1 and 2 fail.
- injection moved before the strip → test 3 fails (and the suite otherwise stays green, which is
  the point of writing 3 as a replacement assertion rather than a presence one).
- the `method`-presence check dropped → test 4 fails.
- batch descent removed → test 5 fails.

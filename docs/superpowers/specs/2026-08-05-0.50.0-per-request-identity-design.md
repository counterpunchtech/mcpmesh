# 0.50.0 design — identity injection on every request (#45 ask 2)

Version: **0.49.2 → 0.50.0 (MINOR)**. `API_MINOR` 56 → **57**.

The draft left `API_MINOR` alone on the grounds that no field changed shape. The gate pointed at
this file's own policy — minor *"also bumps for a change to what a field MEANS with no change to its
shape"* — and at minor **37**, which is that precedent on this literal field. A backend has no other
way to probe "does this daemon attribute every request?"; the crate version is invisible to it.

---

## Why this is startable while #45 stays gated

> **Read the corrected gap section below first.** The original justification for starting — "one of
> #45's asks is already a defect" — did not survive review. What remains is a hardening plus the
> elimination of a duplicated identity rule, which is worth shipping on its own terms but is a
> weaker reason than the one this section was written on.


#45 carries an explicit **"⛔ BLOCKED — do not start yet"** banner naming three gates. Two have since
lifted (rmcp is stable at 3.1.1 and we ship on `=3.1.0`; the `2026-07-28` spec is final). The third —
**real ecosystem adoption** — has not, and it is not being jumped here.

What is being taken is one of #45's three asks — the draft called it "the only one that is already a
defect", which the corrected gap section below retracts:

> **(2) Identity injection** — inject `_meta["mcpmesh/peer"]` (and keep stripping caller-forged
> reserved keys) on **every** forwarded request, not just the first, since there is no single
> handshake to anchor it to. This is the forge-proofing surface — it must remain authoritative
> per-request.

The other two are deliberately left:

- **Ask 1 (routing) needs no work at all**, and the issue's framing of it turns out to be wrong.
  `select_service` reads `/params/_meta/mcpmesh~1service` from whatever the session's first frame
  is — **it never inspects `method`**. A stateless first frame routes correctly today. Ask 1 asks
  whether routing should become *per-request* rather than per-session; that is a real design
  question (it would let one session address several services), it is not forced by vNext, and
  answering it before a counterparty exists is exactly what the ecosystem gate is for.
- **#49 (reverse-DNS key strings) stays blocked.** It is a coordinated wire change both peers must
  adopt together, and this does not touch the key names.

## The gap — corrected, because the first version of this section was wrong

**The draft claimed a session whose first frame is not an `initialize` reached the backend with no
identity at all. That is false, and the gate proved it empirically** by running a probe against
0.49.2: `SocketBackend::run_over` injects `mcpmesh/peer` into frame 1 **unconditionally**, with no
`method` check, on a separate inline code path. A stateless first frame was always attributed.

So the honest gap is narrower:

| | before 0.50.0 |
|---|---|
| caller forges `mcpmesh/peer`, any frame | stripped (`select_service` on frame 1, `sanitize_caller_frame` after) |
| backend learns the caller on frame 1 | **yes**, whatever its method |
| backend learns the caller on a later `initialize` | yes |
| **backend learns the caller on frames 2..N** | **no** |

A backend that binds identity at session start — which is what the pre-0.50.0 docs told backends to
do — was never blind. What was missing is per-request authority: a backend that authorizes each
request independently saw nothing on frames 2..N.

**This was fail-closed, never forgeable.** The strip has run on every frame since `api_minor` 37, so
the backend saw *nothing* rather than something attacker-controlled.

**That reframing changes what this release is.** It is a HARDENING that makes the code match a
promise the documentation already made — `docs/local-protocol.md` said `mcpmesh/peer` was
"stripped-then-injected on every frame", and only the strip half was true — plus the removal of a
duplicated identity rule. It is not a defect fix, and the commit message says so.

## What ships

`inject_peer` injects into **every caller→backend frame carrying a `method`** — requests and
notifications alike — instead of only `initialize`.

Everything else is unchanged and load-bearing:

- **The strip still runs first**, so injection remains authoritative rather than merging with
  anything the caller sent. Order is the security property; it is not being touched, and moving it
  fails seven tests.
- **Batches still descend**, depth-bounded, exactly as `strip_reserved_meta` does.
- **An absent or null `params` is still created**, so a parameterless request gains a well-formed
  object. A non-object one is now left alone instead — see below.

**Frames without a `method` are left alone.** A caller→backend *response* (to a server-initiated
request — #91's push direction) has `id` + `result`/`error` and no `params`; inventing a `params`
object on one would be malformed JSON-RPC. Frame 1 used to do exactly that, and now does not,
because it shares this code.

### The duplicated identity rule, which is the better reason to ship

`run_over` had its own inline copy of the injection for frame 1, and the two had **drifted in three
ways** — the gate found all three and verified each:

| frame 1 (inline) | frames 2..N (`inject_peer`) |
|---|---|
| a response `{id, result}` → `params._meta` **invented** (malformed JSON-RPC) | left untouched |
| a batch → whole frame **discarded**, replaced by a fabricated `{"params":{"_meta":…}}` | descended, each element attributed |
| a non-string `method` → injected | skipped |

Two implementations of one identity rule is the exact #164 drift class this file exists to prevent,
and it was invisible because only `inject_peer` was tested. Frame 1 now calls `inject_peer`, so
there is one rule with one set of tests.

### Positional params are no longer destroyed

`inject_peer` replaced a non-object `params` with `{}` before writing `_meta`. That was near-dead
while injection touched only `initialize` (MCP always sends object params there); widening it to
every request would have made it **silently delete the arguments** of every positional JSON-RPC call
a non-MCP backend received. It now leaves such a frame intact and un-attributed — fail-closed, and
consistent with the module's own rule that the platform pumps rather than interprets.

### The audit hash must not move

`auditor.on_request` runs after sanitization, so hashing the frame verbatim folds the caller's
identity into `AuditRecord.args_hash` — documented as "a digest of the arguments", and published
vocabulary since it rides `subscribe`. The gate measured two peers making an identical call
producing different digests. `args_hash` now excludes `mcpmesh/peer` specifically (everything else
in `_meta` is caller input and still hashes), so the digest is unchanged from before this release.

### Why MINOR rather than PATCH

`RELEASING.md`: breaking bumps the minor, everything else the patch. A served backend now receives
`_meta["mcpmesh/peer"]` on requests where it previously saw none. A backend that validates its
params strictly — a `deny_unknown_fields` handler, a schema with `additionalProperties: false` — can
**reject** requests it used to accept. That is a break in the mesh↔backend contract even though no
signature moved and no control-API field changed, so it is a MINOR, and the release notes say so
plainly rather than describing it as purely additive.

## Testing

1. ~~A non-`initialize` first frame gets the identity.~~ **Already true before this release** — see
   the corrected gap section. `a_later_initialize_cannot_carry_a_forged_peer` (frame 1 = `ping`)
   already covered it.
2. **Every LATER frame gets it**, which is the actual change — and through the REAL backend, not
   only a helper. The gate measured that deleting batch descent, or skipping notifications, each
   failed exactly one `sanitize_caller_frame` unit test while the whole socket path stayed green.
3. **A forged `mcpmesh/peer` is replaced, not merged**, on a non-`initialize` frame. This is the
   ordering property; a test that only checks presence would pass on an implementation that injects
   *before* stripping and therefore ships the caller's value.
4. **A response frame is untouched** — no `params` invented on a frame that has no `method`.
5. **Batches**: every element with a `method` is injected, depth-bounded.
6. **The legacy path is unchanged**: an `initialize` first frame behaves exactly as before.

### Mutations to run

- the injection restricted back to `initialize` → 3 tests fail, including the real UDS one.
- notifications skipped (`id` required) → 2 fail, including the real UDS one.
- batch descent removed → 2 fail, including the real UDS one.
- the caller's identity folded into `args_hash` → `the_injected_caller_identity_does_not_change_the_args_hash` fails.
- positional params replaced instead of skipped → the odd-shapes tests fail.
- injection moved before the strip → test 3 fails (and the suite otherwise stays green, which is
  the point of writing 3 as a replacement assertion rather than a presence one).
- the `method`-presence check dropped → test 4 fails.
- batch descent removed → test 5 fails.

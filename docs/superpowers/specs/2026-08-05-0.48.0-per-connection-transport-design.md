# 0.48.0 design — per-connection idle timeout on the dial path (#166)

Version: **0.47.0 → 0.48.0 (MINOR)**. `API_MINOR` 53 → 54.

Closes #166.

---

## The ask, and the objection it raises against itself

> `ConnectOptions::with_transport_config` exists and `connect_with_opts` consumes it … 0.28.0
> shipped only the node-wide `[network]` knobs, which means a chat session, a bulk blob transfer,
> and a media flow all share one compromise.
>
> **The limitation the reporter did not mention, and it matters.** This is outbound only. An
> *accepted* connection is built from the endpoint's server config, which has no per-connection
> seam. … **Any design here has to say what happens on the accept side rather than quietly deliver
> half the feature.**

That objection is the whole design question, and answering it properly makes the feature smaller and
more honest than it first looks.

## The accept side: not half a feature, because of how QUIC negotiates

`max_idle_timeout` is **negotiated to the minimum of the two peers' advertised values** (RFC 9000
§10.1). The tree already documents this for the node-wide knob, and it decides everything here:

- **Lowering works one-sidedly.** A dialer that wants *this* connection cut quickly when it goes
  quiet gets exactly that, whatever the peer advertises.
- **Raising does not work one-sidedly — from either side.** A connection survives only as long as
  the *shorter* of the two timeouts, so raising it needs both peers configured. That was already
  true of the node-wide knob, and no per-connection seam on either the dial or the accept path
  changes it.

So the accept side is not a missing half. The direction that *can* work unilaterally is fully
available on the dial path; the direction that cannot was never available anywhere. An accepted
connection uses the node default, and a node that wants a shorter timeout on a session it did not
initiate can dial instead — which, for the messaging app in the issue holding one session per peer,
is a real answer rather than a deflection.

Stated in the docs in exactly those terms, because "outbound only" on its own reads like a
limitation to be fixed later, and it is not.

## Keepalive is deliberately NOT offered per-connection

iroh caps the per-path keepalive at 5s and silently discards anything larger, so a per-connection
keepalive could only make pings *more* frequent. The node-wide knob already **refuses** values above
that cap rather than accept a setting that does the opposite of what it says (#56 gate). Offering
the same knob per-connection would be offering one whose useful direction does not exist.

The issue says the same thing — "it can lower it … the idle timeout is the part with real value
here" — so this follows the ask.

## Surface

`open_session` gains one optional field:

```
open_session { peer, service, idle_timeout_secs? }
```

- Absent → the node-wide `[network].idle_timeout_secs`, i.e. today's behaviour exactly.
- `0` → no idle timeout **from this side**, which still yields the peer's value. Same meaning as the
  node-wide knob, so the two cannot be read differently.
- Validated with the same range check the node-wide knob uses; an unencodable value is a clean
  per-request error, never a silent fallback to the default. A knob that quietly did nothing is
  what #56's gate found and refused.

No `[services.*]` block: a service entry describes what this node **serves**, and this setting
applies when it **dials**. Putting it there would read as governing inbound sessions, which is
precisely the confusion the accept-side discussion above exists to prevent.

## Where it applies, and where it cannot

The single-target dial paths take it: `dial_by_eid`, and the single stored entry. The **racing**
paths (roster person→device, multi-device `user_id`) do not — `race_dial` opens several connections
and keeps the winner, and threading a transport config through would apply it to dials that are
about to be abandoned. A caller that needs a specific timeout for a specific device can name that
device with `eid:`, which is the same answer #41 gives for every other per-device concern.

Documented rather than silently partial.

## Testing

1. **The value reaches the connection.** Asserted on the negotiated `max_idle_timeout` of a real
   connection between two nodes — not on the fact that a dial succeeded. A knob that was never
   applied is invisible to "did it connect", which is exactly what #56's gate caught twice.
2. **Lowering wins over a higher node-wide default**, on a real connection.
3. **The default path is unchanged**: no field → the node-wide value.
4. **An unencodable value is a clean error**, not a fallback.
5. **A racing dial ignores it** — and says so — rather than applying it to abandoned connections.

### Mutations to run

- the per-connection config dropped before `connect_with_opts` → test 1 fails.
- the field parsed but not threaded past the handler → test 1 fails.
- `0` mapped to "unset" instead of "no timeout" → test 3 fails.
- the range check removed → test 4 fails.

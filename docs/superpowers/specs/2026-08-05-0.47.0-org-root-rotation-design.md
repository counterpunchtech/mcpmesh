# 0.47.0 design — org root rotation (#93 ask c)

Version: **0.46.0 → 0.47.0 (MINOR)**. `API_MINOR` 52 → 53.

Closes #93.

---

## The gap

> **(c) The org root cannot rotate.** The schema pins exactly one signature slot against one pinned
> public key. `OrgJoinParams` can pin a new anchor, but nothing migrates membership — so recovery is
> O(N) fresh ceremonies with every member.
>
> Combined with the 90-day default validity, an operator laptop that dies takes the org with it 90
> days later. **The delay is the problem: nobody will connect the cause to the effect.**

That last sentence is the whole issue. A failure that arrives three months after its cause, with no
signal in between, is the kind an operator diagnoses by rebuilding the org from scratch.

## Why the obvious design is not enough

The natural shape — "a successor root carried in a roster signed by the current key" — is right, and
on its own it has a hole worth naming before building it:

A node validates rosters against **one pinned key**. If the successor is announced only in the
roster that introduces it, a node that is offline for that publication never learns the new anchor,
and every later roster (signed by the successor) fails its signature check. That node is stranded
exactly as it is today, and the failure looks identical.

Being offline across one roster publication is not exotic — it is a laptop closed for a week.

## What ships: a cross-signature that rides every roster

Two additive fields:

```rust
/// The org root that SUPERSEDES the one this roster is signed by, `b64u:<ed25519 pk>`.
pub successor_root_pk: Option<String>,
/// The PREDECESSOR root's signature over `domain ∥ org_id ∥ successor_pk` — the bridge that lets a
/// node still pinned to the old anchor adopt the new one.
pub successor_sig: Option<String>,
```

New signing domain `mcpmesh/org-root-rotation/1`, separate from the roster body signature and from
every other domain in the tree, so a rotation statement can never be replayed as a roster, a device
binding, an introduction, or a device revocation.

The rotation then works in two publications, and — the point — **keeps working for a node that
missed either of them**:

1. **Announce.** A roster signed by the CURRENT root carries `successor_root_pk` + `successor_sig`.
   A node validating it against its pinned anchor adopts the successor.
2. **Continue.** Every subsequent roster is signed by the NEW root and *keeps carrying the same
   `successor_root_pk` + `successor_sig`.* A node still pinned to the old anchor verifies the
   cross-signature with the key it has, adopts the successor, and then verifies the roster body with
   it.

So the anchor a node holds only has to be *one* rotation behind, not perfectly synchronised. A node
two rotations behind still needs manual re-anchoring — chaining further would mean carrying a
history, and an operator who has rotated twice while a machine was off can hand it an `org_join`.
Stated rather than left to be discovered.

### Validation order, which is the security of the whole thing

In `validate_for_install`, **before** the body signature is checked:

1. If the roster carries a successor pair AND the body does not verify against the pinned root,
   verify `successor_sig` **with the pinned root** over `domain ∥ org_id ∥ successor_pk`.
2. Only if that succeeds, adopt `successor_pk` as the verification key for this document, and
   continue with rule 1 (body signature) against it.
3. Every other rule is unchanged: the serial must still strictly increase, the validity window still
   applies, and the structural rules still run.

The properties this preserves, each of which is a way to get it wrong:

- **A successor is only ever adopted on a statement signed by the key it replaces.** An attacker who
  can serve a roster cannot introduce their own root — they would need the current root's signature
  over their key.
- **`org_id` is inside the cross-signature**, so a rotation statement for one org cannot be replayed
  into another that happens to share an operator.
- **Rollback protection is not weakened**: adopting a successor does not reset the installed serial,
  so a replayed older roster is still refused.
- **A roster that verifies against the pinned root directly is never re-anchored.** The successor is
  consulted only when the direct check fails, so an ordinary roster cannot silently move a node's
  anchor.

### Persistence

Adopting a successor rewrites `[identity].org_root_pk` through the surgical RMW writer in
`config_write.rs` under `mesh.reload_lock`, like every other config mutation. A rotation that lived
only in memory would revert on restart and re-strand the node — the same "reads as durable, then
silently reverts" failure `#107`'s withdrawal tombstone was designed against.

It is also **audited**: an org's trust anchor moving is the highest-consequence event in roster
mode, and it happens without an operator action on the receiving node.

## Surface

```
mcpmesh org rotate --new-root <path>     # operator side: mint the successor, publish the bridge
```

`org_rotate` takes the CURRENT root key (as `org approve` does) and a path for the new one,
generates it if absent, and emits a roster carrying the pair. It does not distribute anything —
roster distribution is already the operator's problem (`[roster].url` or out of band), and inventing
a second channel here would be a bigger change than the gap.

`status.roster` gains `root_fingerprint_successor: Option<String>` — when a rotation is pending or
recently adopted, an operator can see it. Absent otherwise.

## What this does NOT do

- **It does not recover a LOST root.** If the key is gone, there is nothing to sign the bridge with.
  This makes a *planned* rotation possible and makes an *expiring* org survivable; it is not escrow.
  The issue is explicit that escrow already works by copying `org_root.key` to a second operator
  machine, so the remaining gap really was rotation.
- **It does not chain more than one rotation.** See above.
- **It does not change the expiry model.** The 90-day default and its degradation ladder are
  untouched; rotation is what makes them survivable.

## Testing

1. **The bridge**: a roster signed by the SUCCESSOR, carrying a valid cross-signature by the
   predecessor, installs against a node pinned to the PREDECESSOR — and the node's pinned anchor is
   rewritten, durably.
2. **A forged successor is refused**: a cross-signature by anyone other than the pinned root.
3. **A cross-signature for a DIFFERENT `org_id` is refused** — the replay this field exists to stop.
4. **A roster that verifies directly is never re-anchored**, even if it carries a successor pair.
5. **Rollback protection survives rotation**: after adopting a successor, an older serial is still
   refused.
6. **Domain separation, proved**: a roster body signature must not verify as a rotation statement,
   and a rotation statement must not verify as a device binding, introduction, or revocation.
7. **End to end through two real nodes**: an org rotates, and a member that was OFFLINE for the
   announcing publication still installs the next roster and keeps serving.

### Mutations to run

- the successor path taken when the body verifies directly → test 4 fails.
- `org_id` dropped from the cross-signed preimage → test 3 fails.
- the cross-signature verified with the successor key instead of the pinned root → test 2 fails.
- the installed serial reset on adoption → test 5 fails.
- the config rewrite skipped (in-memory only) → test 1's durability half fails.
